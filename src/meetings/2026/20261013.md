**背景**：在 staging（production snapshot）用 `backfillVertexEmbeddings --limit 1000` 隨機 backfill，成功 999 篇，實際 996 筆向量（TEXT 741，其中 251 篇只有網址；IMAGE 175；VIDEO 80）。模型 gemini-embedding-2、768 維。這是**離線實驗**：從 `airesponses` 讀向量、查詢向量直接呼叫 Gemini，在記憶體算 cosine；沒有經過 ES kNN、BM25 或 hybrid 排序。查詢是把池中文章做變形（加「轉傳：」、「這是真的嗎？」、結尾「請大家轉發分享」、去 emoji／標點、去網址、去追蹤參數、取前半／後半／前 50 字；LLM 改寫、一句話摘要、英譯、越南文、簡體、3–5 個關鍵字），看原文是否排第一、cosine 多少、以及最像的非原文文章（背景值）多高。樣本幾乎沒有「同一謠言不同版本」的天然配對，**量不到真實 recall**。

**重點結論**
1. **`taskType` 對 gemini-embedding-2 沒作用**：`RETRIEVAL_QUERY`／`RETRIEVAL_DOCUMENT`／`SEMANTIC_SIMILARITY` 算出的向量逐位元相同。官方做法是文字前綴：查詢 `task: search result | query: …`、文件 `title: none | text: …`。
2. **只有網址的文章（佔文字文章 34%）黏在一起**：兩個無關的 FB 分享連結 cosine 可達 0.999。RAW 下相似度前 50 組有 46 組是只有網址的文章（33 組連結不同，13 組真重複）；改 EXP_ASYM_SEARCH（前綴＋連結標題摘要）後降為 28 組（12 組連結不同），並出現 6 組內文真的相似的配對。剩下的幾乎都是 FB `share/p`、`share/r` 只拿到登入牆的連結，建議不要為這類文章算向量。
3. **0.7 門檻擋不住雜訊**：RAW 背景值中位數 0.777；全庫 27.9 萬篇時 kNN 實際會變成「取最近 k 篇」。各格式分數尺度不同，門檻需依選定格式重新校準（ASYM_SEARCH 非網址文章背景 p95 約 0.89）。
4. **文字查不到圖片／影片**：圖片 OCR 文字查自己的向量，RAW cosine 中位數 0.62、**100% 低於 0.7**、排第一比例 0；影片 69% 低於 0.7。ASYM_SEARCH 提高到中位數 0.76、排第一 0.62。kNN 是 `bool.filter` + `minimum_should_match: 0` 的硬性過濾，開 hybrid 後文字查詢幾乎不會出現圖片文章，BM25 也救不回來。
5. **近似重複偵測穩、改寫翻譯中等**：轉傳前綴、去標點、簡體、英譯等 cosine 多在 0.85–0.95；只用關鍵字查最弱，RAW 有 26% 低於 0.7。

**格式比較（原文排第一的比例）**：ASYM_SEARCH 幾乎每列都勝過 RAW（圖片 0→0.62、去標點 0.86→0.99、加結尾 0.76→0.94、翻譯改寫約 +0.1）。EXP_ASYM_SEARCH 在查詢仍保留網址時最好（約 0.98–0.99；`url_strip_params` 從 RAW 0.62 升到 0.96），但查詢沒有網址時（取前半、去標點、LLM 改寫）反而變差。`task: fact checking` 前綴結果和 search result 差不多、search 稍好。推測「每篇存兩個向量（原文、原文＋連結內容）＋ nested `score_mode: max`」可各取所長，尚未測。

### Embedding 文字要不要加 task 前綴（[#411](https://github.com/cofacts/rumors-api/pull/411)）

**需求**：任何模態輸入（文字、圖片、影音），都要找出依關聯度混排的圖、文、影音結果；完全相同的文字排第一。

**#411 現狀**：文字加不對稱前綴，media 不加
- 文件：`title: none | text: …`
- query：`task: search result | query: …`
- 原本的 `taskType` 參數 gemini-embedding-2 不支援，所以拿掉

---

需求：以綠皮蕉為例
- query = 影片 + 逐字稿（只能抽到無意義的浮水印）
- 希望能找到所有相關影片 or 相關圖片訊息

---

**[官方文件](https://ai.google.dev/gemini-api/docs/embeddings)**
- 純文字「強烈建議」加前綴
- 文字和 media 合成一個向量時，一般不建議加前綴
    - 多媒體和文字是分開 embed 的 [name=yutin]
    - 多媒體無 embed
    - 文字有 embed
- 有 `task: fact checking | query: …` 這組前綴可以用，文件端格式和 search result 相同。gemini-embedding-2 的文件沒有解釋它；舊模型對應的 `FACT_VERIFICATION` 說明是「找支持或反駁這段說法的證據」
- **沒說明**：純文字 query 加了前綴之後，拿去比沒加前綴的 media 向量會怎樣

**問題**：#411 量到文字 query 對圖片的 cosine 全部低於 0.7，目前分不出原因是跨模態本來就低，還是前綴讓它變低。
- 可能不太發生，格式不同的時候就有很大的差異 [name=yutin]
- 同樣是文字的可能會比較前面，實務上要用文字搜尋到圖片，應該要搜得很精準才對得上 [name=yutin]

**選項**
- A. 不加前綴：文字和 media 都送原始輸入，比較基準一致，但文字找文字可能變差
- B. 維持 #411（search result 前綴）
- C. 依查詢的目的使用不同的 query 前綴，文件向量不用重算：
  - `ListReplies`（找能反駁這則訊息的回應）：改用 `fact checking` 前綴，用途吻合
      - 可能要做一個新的 argument 讓 caller 決定是要 search result 還是 fact checking
  - `ListArticles`（找同一則或相似的謠言）：維持 `search result` 前綴，或依量測結果決定
- D. 一篇文件存兩個向量（加前綴、不加前綴各一個）：成本加倍

**建議**：在 staging 比較 A／B／C，分開量「文字找文字」、「文字找 media」、「media 找文字」三種情況（C 要另外量 ListReplies 的訊息找回應），挑同一則謠言的不同版本（文字、截圖、影片）當資料。cache 有版本機制，切換選項時只要重算向量，不會互相干擾。

**相關但另外處理**：要做到混排，還要解決幾件事：
- 門檻要依模態組合分開設
- BM25 和 kNN 的分數要正規化之後再合併
- 完全相同的文字要明確加分
