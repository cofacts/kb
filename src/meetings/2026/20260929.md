## LINE Bot `request_timeout` 調查彙整

**調查期間**：2026-09-24 ～ 2026-09-29
**觸發原因**：production LINE bot（Cofacts 真的假的｜轉傳查證）持續收到 LINE 的「bot server returned no response or an error」通知信，但手動測試（tutorial、影片查證）都正常。

### 結論先講：找到兩個確定的根因並修掉了，但不確定問題是否已經完全解決，還額外挖出一個舊的未解謎團

---

### 一、症狀與資料來源

- LINE Developers Console 的 bot error stats（`request_timeout` on `POST /callback`）
- Cloudflare GraphQL Analytics API（`httpRequestsAdaptiveGroups`，逐請求層級的 edge 資料）
- GCE `cofacts-prod` 上的 Cloud Logging（`gcplogs-docker-driver`，line-bot-zh 的 application log）
- `journalctl` / `dmesg`（OS 層級事件）

錯誤從至少 2026-09-11 就存在（Gmail 訂閱信可查），9/21～9/24 明顯加劇（LINE 統計：30 → 55 → 40 → 96 次/天），之後回落。

**關鍵前提**：確認 `/callback` 流量本身在整段期間持平（每天 9,700～13,000 次，無成長趨勢）——**不是使用量變多造成的**。

---

### 二、根因 #1：Node 預設 `keepAliveTimeout`（5 秒）與 reverse proxy 連線重用視窗不匹配

- `rumors-line-bot/src/index.js` 的 `app.listen()` 從未設定 `keepAliveTimeout`／`headersTimeout`，用 Node 預設 5 秒。
- 前面是 Cloudflare Tunnel（`cloudflared`），會保留、重用比 5 秒更久的 keep-alive 連線。
- Node 在閒置 5 秒後主動關閉連線，若此時 cloudflared 剛好要重用同一條連線送新的 webhook 請求 → 連線已死 → LINE 收不到回應 → 記錄成 `request_timeout`。
- Cloudflare edge 資料佐證：`/callback` 上 **499（client/edge 等到放棄）有 300 次，真正的 502（origin 主動回錯）只有 6 次**，符合「連線被晾在那沒人接」的特徵，而非 app 邏輯出錯。

**修法**：`server.keepAliveTimeout = 65_000`、`server.headersTimeout = 66_000`（拉到明顯大於 proxy 的重用視窗）。

**PR**：[cofacts/rumors-line-bot#416](https://github.com/cofacts/rumors-line-bot/pull/416) — 已 merge、已部署（2026-09-26 08:21 UTC 重啟生效）。

**效果**：部署後，「短時間內同一分鐘炸裂好幾筆」的密集錯誤模式消失了；但**零星、單筆的失敗並未歸零**，代表這不是唯一成因。

---

### 三、根因 #2：每小時的 PM2 reload（cron）在 SIGINT 時沒有優雅關閉

查 `/etc/cron.d/cofacts-ops` 發現：

```
# Chatbot group 重啟（穩定性維護）
15 * * * *  root  cd /srv/rumors-deploy && docker compose exec -T line-bot-zh node_modules/.bin/pm2 reload all ...
```

line-bot-zh **每小時被 `pm2 reload all` rolling-restart 一次**（透過 Cloud Logging 查證，至少從 9/14 起、每小時精準地在 :15:0X 秒發生）。

- `pm2 reload all` 對舊 worker 送 `SIGINT`，但 `src/index.js` 原本的 SIGINT handler 沒有呼叫 `server.close()`，直接 `redis.quit()` 後 `process.exit(0)`——舊 worker 手上任何 keep-alive 連線（含閒置中的）都被瞬間砍斷，不管 Node 自己的 `keepAliveTimeout` 設多少。
- PM2 預設 `kill_timeout` 只有 1.6 秒，就算想優雅收尾也沒時間。
- **時間點對得上**：部署 #416 之後殘留的失敗裡，換算成 UTC 後有兩筆精準落在 `:15:15`（reload 那一分鐘），隨機撞上同一秒附近的機率極低。

**修法**：SIGINT handler 加 `server.close()`（先停止接受新連線），`ecosystem.config.js` 的 `kill_timeout` 拉到 15 秒（給收尾時間）。

**PR**：[cofacts/rumors-line-bot#417](https://github.com/cofacts/rumors-line-bot/pull/417) — **已開，尚未 merge / 部署**。

9/22 台灣時間凌晨 03:34～04:56，Cloudflare 自己內建的 health check 打 `line-bot.cofacts.tw/` 有 ~30% 收到 502（持續約 50 分鐘）。查了 `dmesg`／`journalctl`，**沒有 OOM、沒有 container 重啟紀錄**——origin 當下應該是「活著但卡住沒回應」，原因不明（舊 container log 已隨 9/26 部署被換掉，回不去查了）。這單一事件把 9/22 當天的錯誤數字拉得特別高，跟根因 #1、#2 是分開的事，暫時懸而未決。

### 五、順著 cron 註解「Chatbot **group** 重啟」牽出的舊謎團（尚未解決）

- 這個 cron 的原始目的，據 Johnson 回憶，是拿來解決「**群組訊息處理有時候沒回覆**」的問題——用定期重啟當作 workaround。
- 查 git log：`src/webhook/handlers/groupHandler.js` 用 Bull queue 處理群組訊息，有一段刻意設計的「過期事件暫停/恢復」邏輯（`84c9d2e`，2018年commit，設計意圖：有新事件時暫停處理過期事件）。
- **Johnson 自己在 2023-02-06 就寫過 debug commit**（`ad63cf8`：「Add debugging log to group - Helps check why group chatbot has no reply when the queue still works」），後續又加了 GraphQL queue 監控端點——顯示這個「群組有時候沒回覆」的謎團**至少 3 年前就存在、當時也沒真正查出根因**，只留下診斷工具。
- 這次重新檢查程式碼，發現 `pause()`/`resume()` 沒有帶 Bull 的 `isLocal` 參數（理論上在 production 實際跑的 3 個 PM2 cluster worker 之間，這是全域生效的暫停，可能有「暫停後沒人恢復」的風險）。**但嘗試修正後發現：**
  - 會直接弄壞既有測試（`groupHandler.test.js` 斷言 Bull 的 `paused` job count，只有全域 pause 才會出現這個數字）
  - 會讓 2023 年加的 GraphQL 監控（`QueueInfo.isPaused`）失去效用
  - 重新想過 Bull 的 `'drained'` 事件其實會廣播給所有 worker，不是只有暫停者能恢復，所以「永久卡死」的推論也沒有很確定
  - **最終沒有送出修復 PR**，決定先不動這段 code，避免弄壞更多東西卻沒解決真問題。
