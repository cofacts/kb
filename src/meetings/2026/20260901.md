## Log retention TODO 調查結果（2026-08-19）與執行狀況

### TODO 1：分析 cloudflared logging 是否記錄 IP / 搜尋過往討論 / 讓 GCP log 收得到 cf-connecting-ip

- **cloudflared 本身的 log level 與此無關**：`--loglevel debug/info` 只記錄 cloudflared daemon 與 Cloudflare edge/origin 間的連線活動，不是 HTTP access log。真正決定拿不拿得到 IP 的是 **origin app 有沒有記錄 Cloudflare 加的 `cf-connecting-ip` header**
- **現況盤點**（實查 GCE 上的 gcloud logging + 各 repo 程式碼）：
  - ✅ `rumors-api`：`src/index.js:37-42` 用 `koa-pino-logger`（`LOG_REQUESTS=1` 時啟用），預設記錄完整 request headers（含 `cf-connecting-ip`），已在送 GCP Cloud Logging
  - ❌ `rumors-site`（site-en/ja/zh/old）：完全沒有 request logging；PM2 `ecosystem.config.js` 還把 `out_file`/`error_file` 導到 `/dev/null`，架構上不會有 log
  - ❌ `line-bot-zh`：抽樣 100 筆沒看到 header/IP
  - ❓ `url-resolver`：純文字 log，沒有 header/IP
- **過往討論**：只有 `kb/2026/20260505.md` 提過一句「空 headers 代表沒有 cf-connecting-ip，即從內部 Docker network 進來」，沒有更早的專門討論
- **挖出的歷史脈絡**：AWS 時代（~2023 前）nginx 是 reverse proxy，nginx access log 本身就有 client IP、且接到 CloudWatch；**2025-09-28 production 移除 nginx 改用 cloudflared 後，這個 log 來源就消失了**，且 `20251014.md` 已經記錄過一次「找不到 request log」的踩坑。目前 `rumors-api` 的 pino log 是**全站唯一**還留著真實來源 IP 的 log 來源
- **額外發現的 bug**：2023-08-17（PR #312）設計「GraphQL 層 log 只留 IP、pino log 留完整 header，兩邊用 IP 比對」，但 2025-06-22 的兩個 commit（`9bdd69c`、`5e11e27`）把 `Array.from(http.headers.entries())` 改成 `Object.entries(http?.headers ?? {})`，導致 GraphQL log 的 `headers` 欄位一直是空 `{}`——這個比對機制目前已失效，需要修

### TODO 2：研究 GCP log retention 與 log sink 機制（含費用）

- **現況**：`_Default` bucket retention 30 天、`_Required`（audit）400 天，都是 GCP 預設值；**沒有任何自訂 sink 導到 GCS/BigQuery**
- **之前討論過，非新問題**：`2023/20230817.md`（AWS CloudWatch 56GB/月 $43 的成本危機）、`2023/20231101.md`、`2024/20240916.md` 都討論過但從未落地；`2025/20250421.md` 提過「至少一個月」
- **實際用量**（Cloud Monitoring `byte_count` 量測，2026-08）：全 project 約 **25-27 GB/月**，還在 Cloud Logging 50 GiB/月免費額度內，**目前 ingestion 完全不用錢**——比 2023 年那次危機小了 10 倍以上
- **費用估算**（[Google Cloud Observability Pricing](https://cloud.google.com/products/observability/pricing)：ingestion 超額 $0.50/GiB，30 天以上 retention $0.01/GiB-month）：
  - 方案 A：直接拉長 Cloud Logging bucket retention 到 1 年 → 約 **$2.75/月**
  - 方案 B：GCS sink + BigQuery external table（只在需要時 query）→ GCS 儲存 **$1.2~$6/月**（視 storage class），BigQuery 查詢 $6.25/TiB scanned、每月前 1TiB 免費，單次查一整年份都在免費額度內
  - **兩種做法在目前量下都便宜到可忽略**；方案 B 的優勢是能用 SQL 查結構化欄位，解決現在 log 是一整包字串、只能 regex 找的問題
  - ⚠️ 若之後把 `rumors-site`、`line-bot-zh` 也比照 `rumors-api` 開完整 header logging，總量可能明顯上升，屆時免費額度可能撐不住

### 補充：Cloudflare 端的 Analytics retention 與匯出可能性

- **Retention（Business plan）**：`firewallEventsAdaptive`（WAF 攔截事件）只留 **3 天**；`httpRequestsAdaptive`/`httpRequestsAdaptiveGroups`（一般流量分析）留 **31 天**——後者就是 `Cloudflare.md` 記錄的「~4 週」traffic table 的資料來源，前者（WAF 事件）比想像中短很多，之前文件沒特別標出來
- **匯出到 GCP**：
  - **Logpush**（Cloudflare 官方、可直接推到 GCS 的原始 log 匯出機制）：**需要 Enterprise plan**，Business plan 完全用不了，跟 TODO 2 查到的結論一樣是死路
  - **自建排程打 GraphQL Analytics API**（Business plan 可行）：可以延長「聚合統計」的保存期，但這是**聚合過、可能被 sampling 的資料**，不是逐筆原始 log，救不了真正的 forensics 需求
  - 若團隊真的需要 Cloudflare 端逐筆可回溯的 log，現實選項只剩「升級 Enterprise」或「全部靠 origin app 自己的 log」（也就是 TODO 1 在做的事）

2. 記錄 Cloudflare 端 Analytics retention 現況（31 天/3 天）與匯出限制（Enterprise-only），需考慮第 1 點落地後的用量成長
