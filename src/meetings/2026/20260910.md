### User-level memory：Langfuse session 分析（[cofacts/ai#125](https://github.com/cofacts/ai/issues/125) 後續）

> Issue: https://github.com/cofacts/ai/issues/125


接 [20260818](https://github.com/cofacts/kb/blob/main/src/meetings/2026/20260818.md) 的兩件事：#125 的「觀察 session 裡使用者是不是會一直重複某些 prompt」，以及「用 AI + Langfuse skill 找找看使用者敘述的 session 是什麼」。翻了 Langfuse production 資料 + 讀了 ADK 1.26.0 原始碼與 Vertex 文件。

**結論：值得做，但只值得做窄版的 —— per-user 的「編輯約束清單」，不是通用的對話式記憶。建議用 Vertex Memory Bank 當儲存層，V1 只用它的 CRUD、不用 LLM 自動萃取。成本實質上 $0。**

**資料範圍**：`environment=production`，2026-07-29 ~ 09-09
- 226 turns / 80 sessions / 14 位使用者（production 全部有登入，memory 有可靠的 key）
- 4 位重度使用者佔 65/80 sessions（81%）、209/226 turns（92%）
- 232 次 `draft_factcheck_response`（平均每 session 3.2 次，最多一個 session 15 次）
- 分類分佈：RUMOR 107 / NOT_RUMOR 86 / OPINIONATED 39
- latency median 125s、p90 310s；6 週總花費 $20.07
- 註：session 是長命的，會跨天（有一個從 08-07 用到 08-12），「session」≠「一次坐下來」

#### 儲存層：`user:` state vs Memory Bank

[#125](https://github.com/cofacts/ai/issues/125) 寫「ADK user-level session 可以記錄 memory，只要設計一個 tool 就行」—— 這個猜測成立，但要分清楚**三件不同的東西**：

1. **ADK `user:` session state** — 存我們自己的 Postgres（`StorageUserState`），scope `(app_name, user_id)`
2. **ADK `BaseMemoryService`** — 對話片段形狀，`search_memory(query)` 檢索
3. **Vertex Agent Engine Memory Bank** — 真正的後端服務，有自己完整的 REST API

**(2) 是 (3) 的一層薄且有損的 wrapper，評估 Memory Bank 不該用 ADK 的介面去評估它：**

- `preload_memory` 拿**使用者當下這一輪的訊息**當檢索 query（`user_content.parts[0].text`）。而 `sPyB` 23/23、`_1YnAG8` 20/20 的開場訊息是**裸 Cofacts URL** --> 拿 URL 去檢索永遠撈不回「不要引用中時」，**會在最需要它的兩位使用者身上、在第一個 turn 就失效**
    - 但 Memory Bank 原生支援 **scope-only retrieval**：`memories.retrieve(scope={"user_id": X})` 可以「retrieve all memories within the scope」，不需要 query，是確定性的
- ADK 的 HTTP 層只有一支 `PATCH /apps/{app}/users/{uid}/memory`（把整個 session 灌進去），**沒有 list／get／delete**
    - 但 Vertex 的 `reasoningEngines.memories` **有完整 CRUD**：`create`／`get`／`list`／`patch`／`delete`／`retrieve`／`generate`
- ADK 的 `add_memory()` 只吃 `MemoryEntry`（Content 形狀），而 Memory Bank 原生支援 `memories.create(fact="...", scope={...})`

--> **結論：繞過 `BaseMemoryService`，直接用 `vertexai` client 打 Memory Bank。** 用 Memory Bank，但不用 ADK 的 memory 整合。

**錢：我們這個規模實質上是 $0**（Memory Bank 2026-09-01 才開始計費，之前 preview 免費）

| 資源 | 免費額度／月／帳號 | 超出後 | 我們的用量 |
|---|---|---|---|
| Agent Storage | **1 GiB-month** | $0.30/GiB-month（含 revisions） | 14 使用者 × 10 條 ≈ **30 KB** |
| Agent Compute（讀） | **50 vCPU-h** = 1.5 億次讀 | $0.085/vCPU-h（300 萬次讀 = 1 vCPU-h） | 6 週 226 turns |
| Agent Compute（寫） | 同上 = 5 千萬次寫 | 100 萬次寫 = 1 vCPU-h | 6 週個位數 |

- 唯一要錢的是 model tokens（「memory generation and embeddings are billed separately under their respective model SKUs」）
- **V1 用 `memories.create(fact=...)` 寫我們自己萃取好的偏好 --> 沒有 generation 的 model call --> $0**
- 未來做 `generate` 自動萃取（= #125 第二層）：實測 session transcript 是 25k–170k tokens（median 47k），照我們自己 Langfuse 記到的實際單價 $0.364/1M input，**一次 consolidation ≈ $0.017/session，80 個 session ≈ $1.4／6 週**（現有花費的 7%）

**Region：asia-east1（台灣）支援，v1 GA** —— 跟現有 Cloud Run + Cloud SQL 同區。Memory Bank 不支援的只有 Jakarta／Melbourne／Toronto。
- ⚠️ 但用 `global` endpoint 就不能用 CMEK（KMS 需要固定地理邊界）。我們現在是 `GOOGLE_CLOUD_LOCATION=global`

**Memory Bank 相對 `user:` state 的三個實質優勢**

1. **user-scoped 資源自帶 CRUD** --> 設定頁直接對它讀寫。`user:` state 只有 session-scoped 的 endpoint，設定頁得借一個 session id 或自己補一支 BFF endpoint
2. **不汙染 session payload** --> `list_sessions()` 會把 user state merge 進**回傳清單裡的每一個 session**（`sPyB` 有 45 個 session，1KB 的 memory 會被複製 45 次）；Memory Bank 沒這問題
3. **`scope` 是任意 dict（上限 5 個 key）** --> `{"user_id": X}` 放個人偏好、`{"user_id": X, "category": "醫療保健"}` 放分類 playbook，發現 3 用同一套機制就解決。另外 TTL 內建

**缺點**

1. 新的 GCP 依賴：一個 `reasoningEngine` 資源 + IAM（`client.agent_engines.create()` 不帶參數就好，**不用部署 agent**，沒有 runtime 要維運）。**prod／preview／staging 必須分開**，否則 preview 會寫進正式使用者的記憶
2. 繞過 ADK 抽象 = 自己維護一層薄 client，ADK 之後改進 memory 整合不會自動吃到
3. 熱路徑多一次外部呼叫 --> 要 fallback：retrieve 失敗就當沒有偏好繼續跑，別讓查核卡住
4. **資料放在 Google 而不是我們自己的 Postgres** --> 見下方待拍板

#### 可見性與隔離

可見性照 Claude 的作法（[參考](https://claude.com/blog/claudes-memory-works-everywhere-and-you-decide-whats-in-it)）—— 看得到、改得動、關得掉、有隔離：

- 設定頁一個「我的查核偏好」清單，顯示全文、可逐條刪除、可整體關閉；預設 opt-in
- 每條記下來源（哪個 session、什麼時候、因為哪句話）
- 每次套用時在回覆開頭一行講明「（已套用你的 2 條偏好：⋯⋯）」--> 可被察覺、可當場否決
- **只記「how」不記「what」**：記表達方式，不記事實、不記結論
- **只記表達偏好，不記結論偏好** —— `AVriAlOoyrDaTqlmmqhC` 有 13/15 個 session 開場就帶自己的判斷，如果 memory 學成「這個人希望結論偏向 X」，就做出一台 confirmation bias 機器而不是查核工具。這條界線建議寫死在 prompt 裡
- 這兩點在 Cofacts 特別重要，因為**查核回覆是公開的、社群共有的**。把「絕對不要引用聯合報／中時／東森」寫進某位查核者的 profile，等於把一位編輯的媒體政治觀點固化進公開查核回覆

隔離立場：**memory 是私人的。session 分享出去只分享對話內容；別人接關時只載入對話內容 + 接關者自己的 memory。** 跟 [#124](https://github.com/cofacts/ai/issues/124) 一起看：

- **Memory Bank 在這點明顯較安全**：memory 不在 session 物件裡，`get_session` 不會 merge 它進來
- **若選 `user:` state，#124 目前的規劃會漏**：#124 寫「從 ADK session ID 找 user id 才能 load session」，而 `get_session(app_name, user_id=<原作者>, session_id)` 會把原作者的 `user:` state merge 進 `session.state` --> 唯讀模式直接把 state 交給瀏覽器就洩漏了。**BFF 唯讀路徑必須濾掉所有 `user:` 前綴 key**
- 另外 `list_sessions(user_id=None)` 會撈出 app 底下**所有使用者**的 user state --> #124 的公開 session 索引很容易踩到
- #124 的「讓 agent 參考其他 public session」那個 tool 也不該去 retrieve 原作者的 memory
- 接關本身是安全的：新 session 建在接關者自己的 `user_id` 底下
- **一個必須誠實講的限制**：偏好是使用者打在對話裡的，tool call 也是 event。所以 session 公開後「這個人不信任聯合報」還是會從對話紀錄看得出來。我們能隔離的是「儲存的 profile 不外流、不套用到別人身上」，不是「這個人的偏好不被看見」

---

#### 效益的誠實估計

- 可省掉的 turns：約 **15–25 個 / 6 週**（佔 follow-up turns 的 10–17%）
- **省的錢：$0.75–1.25 / 6 週。零錢。所以這件事的價值不在省成本**
- 真正的價值：
    1. 使用者不用每個 session 重打同一段話（`xPyH` 那條媒體名單打過至少 4 次，每次 60+ 字）
    2. latency median 125s / p90 310s --> **少一輪就是少等兩分鐘**
    3. 第一份草稿的採用率

**建議的成功指標**（都有現成 baseline）

| 指標 | 現況 |
|---|---|
| turns/session | 2.8（重度使用者 1.7–5.7） |
| 帶來源／篇幅指正的 turn 比例 | 43/226 = **19%** |
| drafts per session | **3.2** |
| 單 turn 就結束的 session 比例 | 36/80 = **45%** |

#### 建議的 V1 scope

1. 一個 `remember_editorial_preference(preference, kind)` tool，writer 只在使用者給出**跨訊息都適用**的指示時呼叫。`kind` 二選一：`sources`／`style`。**不做自動偵測**
2. `memories.create(fact=..., scope={"user_id": X, "kind": ...})`；讀取用 `memories.retrieve(scope={"user_id": X})`。硬上限約 10 條、總長約 800 chars，超過要求使用者先刪。**不呼叫 `generate`**
3. 注入用 `before_model_callback`（writer 已經有 `inject_article_attachment` 這個 pattern），接在既有 Step 2 constraint list 前面。比 instruction 的 `{user:xxx}` templating 安全 —— 後者 key 不存在時會炸
4. 設定頁「我的查核偏好」：可看、可逐條刪、可整體關閉
5. prod／preview／staging 用不同 Memory Bank 實例或不同 scope
6. retrieve 失敗 fallback 成「沒有偏好」繼續跑

**V1 不做**
- 自動偵測／每週 retrospect（#125 第二層）—— 先看 explicit tool 的採用率；4 位使用者的樣本量還撐不起自動萃取的誤判成本
- 主題 playbook 當 user memory（見發現 3）
- 記任何事實或結論
