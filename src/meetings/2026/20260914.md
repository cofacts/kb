## [cofacts.ai] DB schema 更新：staging & production（vector search embeddings 欄位）

> 對應 TODO：MrOrz 把 DB mapping 送到 staging & production DB

**目的**：套用 [rumors-db#78](https://github.com/cofacts/rumors-db/pull/78)（新增 `embeddings` 欄位，供 [rumors-api#388](https://github.com/cofacts/rumors-api/pull/388) hybrid search 讀寫）與 [rumors-db#80](https://github.com/cofacts/rumors-db/pull/80)（ES9 client 的 `reloadSchema` 修正）。兩者皆已 merge 進 `rumors-db` master（`7bccbfd`）。變更為 additive、backward-compatible，`articles` / `replies` 新增 nested `embeddings.vector`（768 維 `dense_vector`，cosine similarity，`hnsw` index），`airesponses` 新增 `embeddings`（`object` / `enabled: false`，做 cache 用）。

### 執行方式

用 `rumors-db` 內建的 `npm run reload -- <index>` 流程（建新 index → reindex → 切 alias → 刪舊 index），對 `articles`、`replies`、`airesponses` 三個 index 各跑一次。

- **Staging（Vultr, answerfamily）**：主機 OS 是 Ubuntu 16.04（2018 年 kernel 4.4），Node ≥18 不論裝在 host 或 container 內都會直接 crash（`uv_thread_create` assertion failure，疑似缺 `rseq()` syscall），無法照 devops/GCE.md 描述的方式在 host 上跑。改用 **SSH local port forward**（`ssh -L 19200:<db 容器 IP>:9200 answerfamily`）把 staging ES 接到本機，用本機的 `rumors-db@master`（Node 22）執行 reload。
- **Production（GCE, cofacts-prod）**：OS 較新（Ubuntu 24.04 / kernel 6.17 / glibc 2.39），Node 24 已透過 nvm 裝好，照 devops/GCE.md 流程直接在 host 上執行（`docker inspect` 找 ES container 內網 IP → 設定 `ELASTICSEARCH_URL` → `npm ci` → `npm run reload`）。

### 結果

**Staging**

| Index         | 舊 index                | 新 index             | Reindex 耗時 |
| ------------- | ----------------------- | -------------------- | ------------ |
| `articles`    | `articles_v1_4_1-v9`    | `articles_v1_5_0`    | 260s         |
| `replies`     | `replies_v1_1_1-v9`     | `replies_v1_2_0`     | 202s         |
| `airesponses` | `airesponses_v1_0_1-v9` | `airesponses_v1_1_0` | 81s          |

**Production**

| Index         | 舊 index                | 新 index             | Reindex 耗時 | 文件數（前 → 後）    |
| ------------- | ----------------------- | -------------------- | ------------ | -------------------- |
| `articles`    | `articles_v1_4_1-v9`    | `articles_v1_5_0`    | 131s         | 294,741 → 294,741 ✅ |
| `replies`     | `replies_v1_1_1-v9`     | `replies_v1_2_0`     | 138s         | 147,830 → 147,830 ✅ |
| `airesponses` | `airesponses_v1_0_1-v9` | `airesponses_v1_1_0` | 77s          | 276,796 → 276,796 ✅ |

Production 有先抓 migration 前的文件數當 baseline，reindex 後三個 index 筆數完全一致，確認沒有資料遺失。Staging 因為是先跑完才想到要驗證，沒有抓到 migration 前的 baseline，改用「reindex 前後 `_count` 內部加總一致」的方式間接確認（`articles` 279,286 + `replies` 143,498 + `airesponses` 249,453 = 三個 index 一起查的 `_count` 672,237，吻合）。

兩邊都確認 `articles` mapping 已正確出現 `embeddings`（nested, `vector`: 768 維 dense_vector, cosine, hnsw）。兩邊目前都還 **0 筆文件有 `embeddings` 值**——這次只更新 schema，實際寫入/讀取 embeddings 的 hybrid search 程式碼（rumors-api#388）尚未部署，屬預期中狀態。

兩邊網站與既有搜尋功能皆確認正常（staging 由使用者手動驗證；production 為既有流量持續運作中，未見異常）。

**重點**：舊網站（2020 改版前）本來就有「查某帳號回報過哪些文章」的功能（`old.cofacts.tw/articles?searchUserByArticleId=xxx`），2020 重寫新網站時沒有搬過去。2021-11-03 這次是「事後發現少了這功能」的討論——mrorz 還指出這樣不對稱（編輯的回應列表有，使用者的回報列表沒有），但 bil 認為時代演進、隱私要求更高了，最後選擇**不重建**這功能，改用「profile page 預設不公開給不特定人、當事人自己決定要不要分享連結」來處理隱私疑慮，而非把回報列表做出來。

### 更早的背景（同一條隱私顧慮的源頭）

- **2017-12-20**（[20171220](https://github.com/cofacts/kb/blob/main/src/meetings/2017/20171220.md)）：orz 提議做「查這個 id 傳了哪些文章進來」，Hazel 隨即點出「但沒有意識到，會公開說是『誰會送出來』」「可能會有使用者覺得不舒服」——同一個顧慮在 4 年後（2021）幾乎逐字重演。
- **2020-08-31**（[rumors-api userId/appId 提案](https://github.com/cofacts/kb/blob/main/src/research/rumors-api-userid-appid-management-proposal.md)）：新網站重寫時其實已經設計好技術方案——用**假名 + 隨機頭像**顯示 reply request 的使用者、支援「列出此使用者所回報的文章列表」，2020-11 也真的把假名/頭像資料 migrate 好了，但最終沒有接進前端 UI（"avatar 但 UI 還不會顯示"）。
- 換句話說：**技術上做得到、也曾經規劃過**，2021-11 是明確選擇不做的那次拍板。

### 給今晚討論的參考

9/10 會議提到的兩個方向都跟 2021 的結論相容：
1. 「builder 用 reply request，API/open data 本來就撈得到」──沒有改變任何隱私邊界，維持現狀即可。
2. 「user profile 頁面加個 tab 顯示這個帳號送過哪些訊息」──**這正是 2021-11-03 決定不做的功能**。如果要重提，2021 年的兩個顧慮（① 使用者不知情、會不舒服 ② 隱私要求只會更高不會更低）需要重新面對，而不是預設可以直接做。當時提出但沒採用的折衷方案是「預設只顯示 badge/contribution chart，使用者可自行選擇要不要打開回報列表 tab」，如果這次要做，這是現成可以參考的緩解方案。

### Alternative：不做在 profile page，做在 `/articles` filter（「我送出的訊息」自助查詢）

**這次真正的使用情境，其實跟 2017/2021 討論的「公開查某帳號送過什麼」不是同一件事**：使用者透過網站送出訊息後，自然會想回頭找自己之前送過什麼——這是「查自己」，不是「查別人」。查了 [cofacts/rumors-site](https://github.com/cofacts/rumors-site) 現有原始碼，這個 alternative 其實幾乎是現成的：

- rumors-api 的 `ListArticleFilter`（`typegen/graphql.ts:1071`）本來就有 **`selfOnly: Boolean`** 欄位：「Only list the articles created by the currently logged in user」——後端用**登入 session** 判斷「currently logged in user」，不是吃一個公開的 `userId` 參數，所以架構上就只能查「我自己」，不會有查到別人的疑慮。
- 但這個欄位目前在 rumors-site **完全沒有接到 UI**：`/articles` 與 `/search` 頁面的「Filter」（`components/ListPageControls/ArticleStatusFilter.tsx`）只做了 `REPLIED_BY_ME` / `NOT_REPLIED_BY_ME`（用 `articleRepliesFrom.userId` 查「我回應過的文章」），沒有對應「SENT_BY_ME / 我送出的訊息」選項去接這個現成的 `selfOnly`。
    - 唯一用到 `selfOnly` 的地方是 `/search` 頁面查 **Reply**（`ListReplyFilter.selfOnly`，「我寫過的回應」），跟 Article 的 `selfOnly` 是不同欄位，目前沒人接。
- 舊網站當年的 `searchUserByArticleId`（[old.cofacts.tw/articles?searchUserByArticleId=xxx](https://old.cofacts.tw/articles?searchUserByArticleId=366qh7y53xhuy&filter=all&replyRequestCount=1)）在新 schema 裡對應到的是 `userId` / `userIds` / `fromUserOfArticleId`——這幾個欄位**仍然存在**於 API，但同樣沒有暴露在網站 UI 上，只給 API/open data/community builder 用（呼應 9/10 會議「API 都撈得到、researcher 也能用 open data 拿」的現況）。

**結論**：`selfOnly` 幾乎是現成的「我送出的訊息」機制，工程量很小（在 `ArticleStatusFilter` 加一個 `SENT_BY_ME` 選項、接上 `filterObj.selfOnly = true`），而且因為它天生只能查「登入者自己」，**完全不會重新踩到 2017/2021 那次「公開他人回報紀錄」的隱私紅線**——不用做使用者可調的公開/隱藏設定，也不需要動 profile page。這跟「查別人回報了什麼」（`userId`/`fromUserOfArticleId`，維持只給 API/研究者用）是兩件事，可以分開處理。

## [cofacts.ai] /report 表單 placeholder 的 accessibility 評估

對應 [20260910 會議記錄](https://github.com/cofacts/kb/blob/main/src/meetings/2026/20260910.md) 的
TODO，範圍是 `cofacts/ai` PR [#138](https://github.com/cofacts/ai/pull/138) `/report` 表單裡
「為何您覺得這是謠言？」的說明 textarea。

### Q1：一般 accessibility 建議

現在的用法沒犯大忌：問題文字是常駐可見的 `<label>`，placeholder 只當範例輔助，不是唯一說明，
所以不會有「打字後說明消失」的問題。原則上 placeholder 不能取代 label、對比度門檻一樣適用，
但這兩點這裡本來就沒踩到。

### Q2：長 example 會不會拖累 Lighthouse 分數？

**不會，實測過。** 把現在的短 placeholder（51 字）跟刻意寫長的 example（281 字，5.5 倍長）各自
做成真實 markup 跑 Lighthouse accessibility 稽核：**兩者都是 100 分**，`color-contrast`、
`label` 等 audit 完全沒差異。

原因：Lighthouse 用的 axe-core 規則**根本不檢查 `::placeholder` 的內容**，所以長度本來就不在
它的稽核範圍內。連帶推論：Lighthouse 綠燈也不代表 placeholder 對真人可讀夠不夠——這件事工具測
不到，得靠人工判斷。

### 附帶發現（本次不處理，設計端會接手）

實測順便量到：`/report` 這兩個欄位（url / reason）沒套用專案共用元件都有的
`placeholder:text-muted-foreground`，吃的是瀏覽器預設灰色 `#757575`，對白底對比度 **4.6:1**
（剛壓過 AA 門檻 4.5:1，margin 很薄）；若套用專案既有的顏色 `#666666` 則是 **5.7:1**。
nonumpa 說的「對比度較低」有實測根據，但這次會議不排入待辦。

5 條引用**在整個 session 的所有工具輸出裡一次都沒出現過**。造假方式是真域名假路徑——investigator 真的找到 `mirrormedia.mg/story/20220613bus001`，交出去的卻是 `…/20170525bus001`、`…bus002`，另外兩條 udn / cna 完全憑空。

**為什麼 gate 沒擋**　`tools.py:544` 只檢查 `source_url` 有沒有出現在 `references` 字串裡，而 `references` 也是 writer 自己寫的。log 顯示 14:22:37 第一次被退（`not present in references`），writer 把假網址貼進 references，14:22:45 第二次就 `success: True`。`verifier_confirmed` 也是 writer 自己填的 boolean。

**提案**　`claim_sources[].source_url` 必須落在該 session 累積的 **verifier ∪ investigator `sources[]`** 裡。

來源不放 ADK state（state 會被 list session API 附在 session list 裡帶出去），改成**在 gate 內遍歷對話紀錄**：ADK 1.26.0 的 `ToolContext` 即 `Context`，繼承 `ReadonlyContext`，其 `.session.events` 就是完整 event list，走訪各 event 的 `function_response`、取出 investigator / verifier 回傳的 `sources[]` 即可。唯讀、零額外儲存。

跨 turn 已實證可行：9/13 14:22 那個 turn 的 writer 第一個 `call_llm` input 裡就帶著 **9/11** 那個 turn 的 investigator `function_response` 與 `sources[]`（events 由 Postgres `SessionService` 載回）。這點很關鍵，因為該 case 的證據是兩天前收集的。同一份 input 裡 `sources` 只出現一次——9/11 的 verifier 被 125s 砍掉沒留下 function_response——正是要擋的情境。

實作上 `draft_factcheck_response` 目前是純函式，需加 `tool_context: ToolContext` 參數（ADK 會自動注入，不會出現在給 LLM 的 schema 裡）。

**回測結果**（歷史 `user-thumbs` 資料，session 層級重建來源集合）

| 規則 | 👍 正面回饋誤擋 (n=69) | 👎 出處相關負評攔截 (n=21) |

- 第三種規則誤擋沒變少、攔截率反而掉，**verifier ∪ investigator 是 Pareto 最優**。
- 那 3 筆誤擋可能高估：其中 `edcc0c71` 該 session 另有 8 個倒讚含「提供不存在的出處」。實際誤擋估 2–4%，且擋下來是要求 writer 重試，不是拒絕服務。
