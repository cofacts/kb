### 清理 production 上的 login wall

建議不要逐筆判斷，改用「同一段內容在很多不同網址重複出現」這個特徵來清。

#### 關鍵：污染內容高度重複

登入牆、錯誤頁、跳回首頁、全站說明這幾類內容，在幾百、幾千個不同網址上會是幾乎一模一樣的 title 或 summary。真正的貼文內容大多只對應一個網址。所以只要找出「重複出現的固定文字」，就能找出大部分污染：

- **不用逐筆呼叫 LLM 或 url-resolver**，掃一次 `urls` index 算 fingerprint 就好，成本很低。
- **title 和 summary 可以分開判斷。** #410 的研究結論本來就是這兩個欄位要分開決定（例如 FB 標題是「登入或註冊即可查看」但內文是真的貼文，YouTube 則相反）。用 fingerprint 也是逐欄位判斷，剛好對上。
- **要人工確認的對象從幾萬個網址變成幾十到幾百種固定文字**，人工看得完。

#### 建議步驟

**0. 先止血。** 先確認新寫入不會再產生污染，否則清完又會一直進來：
- url-resolver#80 已經上 production。
- 下面整理出的「固定文字清單」在 `scrapUrls` 寫入時也套用一次。這等於先做一個規則版的 #409，LLM 判斷之後再說。

**1. 量化。** 寫一個唯讀 script，scroll 整個 `urls` index，只讀 `url`、`canonical`、`title`、`summary`、`status`，不讀 `html`：
- 對 title 和 summary 各自正規化（去空白、數字、網址）後算 hash。
- 輸出每個 fingerprint 出現在幾個不同網址、分布在哪些網域，以及幾個範例。
- `articles` 和 `replies` 的 `hyperlinks` 也照同樣方式掃，它們是另外存的一份資料，不見得和 `urls` 一致。

**2. 人工確認固定文字清單。** 依出現次數排序，從最多的開始看：
- 每種固定文字標記「清 title」、「清 summary」或「都清」，存成 repo 裡的 JSON。
- 數量多的話，可以請 LLM 先標，再用 #410 的 58 筆人工測資檢查準度。這次判斷的對象是固定文字，不是單一網址，所以 LLM 的錯誤影響範圍也比較小。
- 我推測少數幾種固定文字就能涵蓋大部分污染，但要等第 1 步的數字出來才能確認。

> [!Tip] Checkpoint
> - 確認有哪些網域有污染情形
> - 考慮是否要針對該網域特殊處理

**3. 直接清掉，不重抓。** 依清單把 `urls` 和 `hyperlinks` 裡相符的欄位清空：
- 不用連網，結果可預期，而且很快。
- 修改前先把會被動到的文件 dump 到 GCS 或 BigQuery，方便需要時還原。

**4. 只對一小部分重抓。** 條件是「清空後 title 和 summary 都沒了」，而且「url-resolver 現在對這個網域有新規則」（FB、Threads）：
- 用前一輪討論的 admin API 或共用函式跑，要限速，而且要從 production 的 IP 跑。
- 規則是「新結果比較好才覆蓋」。#410 的重抓結果比原本更差（「都不存」從 221 筆變成 348 筆），不能無條件蓋掉。

**5. 長尾的處理。** 不重複的錯誤頁抓不到，但部分可以用規則處理：
- 原網址有路徑、canonical 卻是網站首頁，代表被導回首頁，可以判定為污染。
- `status` 是 4xx 或 410，但 title 或 summary 有值，也可以判定為污染。

剩下的量應該小到可以先放著，等 #409 的 LLM 分類器做好再處理。

**6. 驗證。** 重跑 10/13 的 embedding 評估，或抽一批只有網址的 FB 文章，看 `moreLikeThis` 找到的相關文章還會不會全部黏在一起。

#### 為什麼不用其他做法

- **全部重抓：** 量太大、會被限速，而且重抓結果不一定比較好。另外有些貼文已經刪除，重抓會把原本能用的內容也蓋掉。
- **每個網址都用 LLM 判斷：** 很貴，準度也還沒驗證過（#409 現在正卡在這裡），而且大部分的判斷都是重複在看同一種登入頁。

> 原始 HTML 存檔：[artifacts/20261110-GgCSaXENPjuDR1rkQNcRtR.html](./artifacts/20261110-GgCSaXENPjuDR1rkQNcRtR.html)

**結論：** nDX 給工程師與設計師的交接 brief。目標是用設計讓「查詢訊息的人」變成「回應訊息的人」。漏斗出處是 CCPRIP · Project WTF（`src/research/ccprip.md`），共四段：認知問題 → 使用平台 → 參與培訓 → 產生貢獻。三條核心工作線落在最後一段「產生貢獻」，第四條只做產品內引導。依據是 20261103 的會議記錄與 Phase 3 網站遷移設計文件。

**KR（集中在「產生貢獻」，前三段只做加分項、不設指標）：** KR 1-2 人機協作資料覆蓋 3,000 則訊息；KR 2-1 累積 3,000 份正面評價；KR 3-1 至少 10 位新協作者發布第一篇回應。

**範圍。** 包含：cofacts.ai 對話介面資訊整理（訪談後優化）、`/report` 導引與送出後流程、讓查核協作者回來貢獻的機制與通知、AI agent 對使用者的導引（產品內部分）。不含：網站遷移本身（Phase 3 Track 0–6，已有專案看板）、社群貼文與 LINE 推播等行銷內容、AI 爬蟲放行與能見度（devops）、預算與科目配置。哪些項目放在這份是作者依對話整理的判斷，有放錯請指出。

**四條工作線**
- **A　對話介面資訊整理（核心）。** 問題：AI agent 的英文 thinking、「」包起來的 tool call 與說明文字全部一起出來，使用者看不出哪裡是草稿、哪裡是佐證。設計：先訪談資料建置小組，再重排思考過程、工具呼叫、草稿、佐證的層次與收合（含手機版與長對話）。工程：把串流事件分類、依新稿實作並放進 Storybook；英文 thinking 要隱藏、收合或翻譯，需工程評估成本。靠 Phase 3 **Track 5 AI chat**（`/ai`、`/ai/session/:sessionId`、工具抽屜），Track 5 尚無人認領，要等訪談結果再決定是否合併；token 名稱對應 class 的規則見 cofacts/ai#176。
- **B　`/report` 導引與流程（核心＋前段加分）。** 讓使用者容易把訊息送進來，送出後被引導去協助查核而不是離開。設計：送出完成畫面（看相似訊息回應、補充線索、請求優先查核）、導流頁與分享預覽卡片、抓不到內文時請使用者改傳截圖的流程、「遇到就來回報」說明。工程：`/report?url=&text=&title=` 已定義，Android 分享選單直達在 cofacts/ai#139；iOS 沒有 Web Share Target，需評估「捷徑」；送出後下一步依賴相似訊息搜尋。靠 Phase 3 **Track 3**、cofacts/ai#138、#139、#148（抓不到內文時改上傳截圖）。已決定回報走獨立流程、不放進 AI 對話（見 [20260910](./20260910.md)）。
- **C　讓查核協作者回來貢獻（核心）。** 三個想法：定時挑 low-hanging fruit 給他們；告訴他們「你寫的回應有 N 人覺得有幫助」（類似 Google Maps 對評論者的影響力通知）；找出不煩人的聯繫方式。設計：通知與任務體驗、影響力訊息文案（用訪談測試）、任務清單版型、頻率控制與關閉設定。工程：定時挑候選訊息（已查過的相似訊息、尚未回應）、排除只有網址的文章（占文字文章 34%）與 FB 分享連結只拿到登入牆的、通知管道與排程（先手動或半自動給小組試用再自動化）、正評數據。前例：WTF 第 4 段（每週感謝、每半年再邀請）、[2017](../2017/20171210.md) 的 filter（只有一則回應、我沒回過）、[2023](../2023/20230308.md) ChatGPT 構想、X 的 Request a Note。依賴 vector search（rumors-api#411，staging 驗證中）；9.4% 的相似度查詢命中內容真的相似且已有回應的文章（見 [20260922](./20260922.md)），候選池要先量；「我送出的訊息」filter 見 rumors-site#631。注意：資料建置小組是寫過 400 篇以上回應的資深協作者，驗證的是「回鍋」，新手轉換（KR 3-1）要靠工作坊參與者。
- **D　AI agent 導引（加分，不設指標）。** 使用者自己的 AI agent 查 Cofacts 時，除了回答也能告訴使用者「這則還沒有人回應，可到 `/report` 回報或自己查核」。工程：MCP server 的 `instructions` 與 prompts、文章頁加給 AI 讀的說明；設計：落地頁文字要讓 agent 容易轉述。靠 Cofacts MCP Server 設計文件（`src/technical-design/cofacts-mcp.md`）「待討論」。限制：MCP 安裝門檻高，覆蓋面有限。

**順序。** 先做 A＋C 合併訪談（對象是資料建置小組，一次問對話介面怎麼用、什麼情況會回來）→ 接著 C 的清單試跑（手動或半自動產生 low-hanging fruit 清單，觀察有沒有人回來寫）→ 並行 B 接在 #138、#139 合併之後 → 有餘裕再做 D。

**待設計師與工程師決定：** (1) A 要和 Track 5 合併還是獨立；(2) 英文 thinking 的處理方式與成本；(3) C 的任務清單放在獨立頁面、站內通知，還是 LINE／Discord 推送；(4) iOS 分享入口要不要做；(5) B 送出後的「下一步」選項（設計列候選、工程確認資料是否拿得到）。工作量與負責人尚未估計，認領時補上。

<summary>Artifact 內容摘要：URL Resolver 登入牆調查（2026-11-07）</summary>

**結論：** staging 換上 Cloudflare Browser Run 後，幾篇 Facebook 與 Threads 連結存下的是登入頁或登入彈窗的文字而非貼文內容。調查對象是 cofacts/url-resolver master（PR #74 之後），環境為 dev.cofacts.tw（staging）。改用 Browser Run `/snapshot` 沒有明顯幫助。

**url-resolver 處理流程：** 0. 先跟轉址（FB 遇到 `/login/?next=…` 會取出 `next`，`photo.php` 改走嵌入貼文端點）；1. 用 `CofactsBot/1.0` User-Agent 從主機直接請求並讀 og 標籤，非 200 即失敗；2. 第 1 步失敗或欄位不齊才用 Browser Run 開頁面，summary 取 Readability 正文、og:description 只在 Readability 失敗時才用，最後與第 1 步結果合併，title 與 summary 誰長用誰。

**測試網址與結果（資料庫存下的內容／各來源實測）**
- FB `/share/p/1KfLdr4NqU/`（dev.cofacts.tw/article/30djvoenir8ob）、FB `/share/p/1Ca7DdjTaP/`（article/2gk97g6p647s4）：staging 存下 title「Facebook」加一段登入頁 footer（233 字，例如「Sign UpLog InMessengerFacebook Lite…」）。分享連結先轉到 `story.php?story_fbid=…`，再從 staging 主機與 Browser Run 出口被 302 到 `/login`；只有家用網路請求 `story.php` 才回 200 與貼文。
- FB `/stantaiwan/posts/pfbid0C2x…`（article/2ymc8okkg75vj）：當初存成日文登入牆（title「このページを見るには、ログインまたは登録してください」），但現在從 staging 主機與 Browser Run 都拿得到內容。處理當時的 log 因容器 11/5 重啟已不在，原因無法追查。
- Threads `/@jamster_eatnfun/post/DfZvPFRktL_`（article/8j2bidp56c1f）與同一篇的 `/share/F19A8BvE_`（article/9gpqhncrnqmb）：staging 主機直接請求收到 429，兩種網址都退到瀏覽器。瀏覽器看得到貼文且 og:description 正確，但頁面蓋著「Say more with Threads」登入彈窗，Readability 有時抽到彈窗文字（網頁網址那篇存了 107 字彈窗文字；`/share/` 那篇兩次都存到 25 字貼文內文，只是剛好，不穩定）。家用網路請求兩種網址都正常。

**三個發現**
1. **FB 分享連結的貼文頁，staging 主機與 Browser Run 都被要求登入**（已驗證）。轉址處理本身沒問題。解法已在 staging 主機驗證：把 `story.php` 網址交給 FB 嵌入貼文端點 `plugins/post.php?href=<story.php 網址或 <id>/posts/<fbid>>`，直接請求就拿得到完整貼文；直接把 `/share/p/…` 給嵌入端點不行（回「這則 Facebook 貼文無法使用」）。`resolveFacebookUrl` 目前只對 `photo.php` 這麼做，分享連結第一次轉址的 `Location` 帶有 `story_fbid` 與 `id`，可在跟去 `/login` 前取下。
2. **Threads 被限流，瀏覽器看得到貼文卻抽錯區塊**（已驗證）。同一份渲染後 HTML 裡的 og:description 就是正確貼文，優先讀它即可，也不必處理 429。
3. **FB 一般貼文現在正常，當初的登入牆無法追查**（待查）；之後再出現可對照當時的 `[resolve]` log。

**讓錯誤內容被存下的程式缺口（來自程式碼閱讀，對應 PR #74 合併時寫下的已知限制）：** (1) 瀏覽器結果沒有任何檢查，`threadsMetadata.js` 的佔位判斷只套在第 1 步；(2) 瀏覽器步驟不讀 og:description，summary 一律取 Readability；(3) `ScrapeResult.merge` 的 title／summary 一律取較長的，Threads 貼文常很短，約 106 字的彈窗文案會蓋過真正內容；(4) 比對字串過時（程式比對 `/^Join Threads to share ideas/`，現在的文案是「Say more with Threads」加「…share thoughts」）。不管哪種情況，登入牆文字都以 `status: 200`、`error: null` 存進資料庫；被擋的 FB 連結全存成同一段 footer，在 Elasticsearch 裡彼此高度相似，反而干擾比對。

**建議修法（依優先順序）：** (1) 瀏覽器步驟優先讀 og:title／og:description，缺了才用 Readability；(2) FB 分享連結改走嵌入貼文端點；(3) 偵測登入牆（含日文等語系）並回傳 error，不存成 200；(4) FB 與 Threads 已有 og 文字時，合併時保留，不採用較長的瀏覽器文字（一般新聞網站維持現狀才能存到全文）。

**方法與限制：** staging 存下的內容來自 `dev-api.cofacts.tw` GraphQL 的 `GetArticle.hyperlinks`；staging url-resolver 以 `docker logs` 讀取（`json-file` driver、未送進 Cloud Logging，容器 11/5 重啟，更早的 log 已不在）；Browser Run 測試用 `POST /browser-rendering/snapshot`（`waitUntil: networkidle2`、逾時 30 秒）；Readability 用 url-resolver 內建的 `src/vendor/Readability.js` 在 jsdom 上解析，與瀏覽器內環境不完全相同；Meta 的登入判定、限流與文案隨時會變，結果反映 2026-11-07 當天的行為。
