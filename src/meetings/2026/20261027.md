<summary>Artifact 內容摘要：Cofacts 開發驗證藍圖（2026-10-25）</summary>

> 原始 HTML 存檔：[artifacts/20261027-KjeWMmZjAM8N5aTmRjzAR9.html](./artifacts/20261027-KjeWMmZjAM8N5aTmRjzAR9.html)

**結論：** 技術規劃草案，範圍涵蓋 cofacts/ai、rumors-api、rumors-db、url-resolver、media-manager、devops 六個 repo。目標是讓 PR 在人類看之前已跑過測試、看過畫面、對過需求、做過 review。分兩層：**確定性檢查放 repo 的 GitHub Actions**（便宜、可重現、能擋 merge）；**需要判斷的驗收交給跨 repo 的 Claude「驗收員」**（讀需求、操作 preview、截圖、提出修法），review 排在驗收員之後。

**七點建議**
1. 先補 CI 的洞：cofacts/ai 的 CI 沒跑 vitest（87 個前端測試只在本機跑）；url-resolver 只有 `.travis.yml`，PR 上沒有測試；media-manager 只在 push 觸發；rumors-api 與 ai 之間的 GraphQL schema 完全沒有契約檢查。
2. Coverage 用「變更行覆蓋率 ≥ 80%」當門檻，不設全域門檻（全域落差大：adk 77%、前端 20%）；不需測的檔案寫在設定檔排除，行內 ignore 只用於少數防禦性分支並附理由。
3. 驗收員用 Claude Code routine，由 CI／Deploy 完成後呼叫 `/fire` API 觸發；可一次 clone 多個 repo，需求來源讀 PR 連結的 issue、GitHub Project（org project 12）、kb 會議記錄與 design doc。找不到需求就明說「只做 regression」，不腦補。
4. 登入問題：staging 建專用測試帳號（如 `cofacts-ai-e2e`），用 staging 的 JWT 私鑰經既有 `signLongLivedJWT(userId)` 簽 token，Playwright 直接設 `cofacts_session` cookie，不走 OAuth。**前提：staging 與 production 的 JWT 金鑰必須不同**；不建議在 preview 加測試用登入 route。
5. Code review 沿用 Vertex billing，不用個人 subscription 的 OAuth token（綁單一使用者額度）。
6. 漏洞修補：私有的 cofacts/devops 開票、評估、測試，人類加 `approved` label 後才在公開 repo 開 PR。需要能讀 Dependabot alerts 的 GitHub App／token（Claude GitHub App 沒這權限）。
7. 方案：先全員 $8 nonprofit Standard 席位 + 開 extra usage 設上限，跑一個月；超過 $32/月的人（主要是掛 routine 的那位）升級 $40 席位。

**現況盤點（2026-10-25，本機實測 coverage）**
- ai（adk）：pytest、ruff、ty；178 tests，lines 77%、branch 65%；`tools.py` 只有 12%。
- ai（src）：ESLint、Prettier、tsc，**沒跑 vitest**；87 tests，lines 20%；每個 PR 有 Cloud Run preview（tag `pr-N`）；Storybook 在 cofacts/ai#154 審查中。
- rumors-api：lint、typecheck、jest（ES 9.3.2）、Coveralls；411 tests，lines 87%（無 `collectCoverageFrom`，未被 import 的 11 個檔案不算分母，87% 偏高；全檔 81%）；`ListReplies` 測試預設 heap 會 OOM；雲端整合測試只在每晚 `integration.yml`。
- rumors-db：lint、typecheck、schema 載入、seed、zod scan；無單元測試；沒檢查 mapping 變更是否升 `VERSION`；rumors-api 的 submodule 落後 2 個 commit。
- url-resolver：PR 上無檢查（Actions 只 build/push image）；7 suites 未量測；jest 23、eslint 7。
- media-manager：lint、test、build、Coveralls，只在 push 觸發；8 tests、lines 55%；`MediaManager.ts` 僅 9%。
- proto：url-resolver 的 `.proto` 在 rumors-api、ai 各有 vendored copy，`UNKNOWN_SCRAP_ERROR` → `UNKNOWN_SCRAPE_ERROR` 改名但編號同為 6，線上相容；建議不追求逐字同步，改在 url-resolver CI 跑 `buf breaking`。

**優先補的測試：** `adk/cofacts_ai/tools.py`（含 `draft_factcheck_response` 的 claim_sources 檢查）、`agent.py` 的 `append_grounding_sources`、`media_filedata.py`（換 Claude 模型 #162 最容易出事）、前端 `chatCache.ts`（SSE reducer）、`run-sse.ts`、`chatSessions.functions.ts`／`articles.functions.ts`、rumors-api 的 `checkHeaders.js`／`adm/util.ts`（安全邊界，覆蓋率 4%／0%）與 `auth.js`、GraphQL `printSchema` snapshot、media-manager 用 `fsouza/fake-gcs-server` 讓整合測試在 PR 上跑、url-resolver `scrape.js`、rumors-db mapping 改動必升 `VERSION`。CI 面：ai 加 `pnpm test -- --coverage`（`@vitest/coverage-v8@3.2.4`；先釘住 `nitro`）、url-resolver 搬到 Actions、media-manager 觸發改 `[push, pull_request]`。

**PR 自動驗證流程：** PR 開啟 → repo CI 跑測試／coverage／契約檢查，cofacts/ai 部署 preview → Deploy 成功後 curl 驗收員 routine → 驗收員蒐集需求（PR 內文「需求來源」欄位、`Closes #N` issue、kb 會議記錄、design doc／ADR）→ Playwright 操作 preview（Storybook、未登入、登入後聊天 smoke）→ 在 PR 維護**一則**置頂留言（需求對照表、截圖、失敗項目與建議修法）→ 通過後才觸發 code review。Regression 不重跑單元測試，改做 Storybook staging vs preview 截圖比對、3–5 段端到端 smoke 對話（確認有 `sources`、引用網址真的出現在工具輸出；呼應 cofacts/ai#144）、改到 prompt／模型時抽 cofacts-ai-eval（cofacts/ai#143）小樣本。截圖貼 GitHub 首選 `gh pr comment --attach`（gh ≥ 2.99.0，需在 Actions／routine 環境升級），備案為 orphan branch `pr-screenshots`。

**跨 repo 契約檢查（repo 層級）：** rumors-db → rumors-api（PR 換 submodule 跑 rumors-api 測試）；rumors-api → ai（ai 的 `codegen.ts` 目前讀 production schema，CI 也沒跑 codegen；建議 `printSchema` snapshot + 在 rumors-api PR 以其 schema 跑 ai 的 codegen 驗證 + ai CI 檢查 codegen 產物一致）；url-resolver → 其他（`buf breaking`）；media-manager → rumors-api（升版跑 typecheck）。結論：契約檢查放 repo 層級，功能驗收放 routine；rumors-api 沒有 preview，端到端要等 PR 上 staging 後補驗。

**Code review：** 比較官方 Claude Code Review（多 agent、有驗證步驟、按 token 計、可設月上限）、`claude-code-action` + Vertex、個人 routine。建議：計費沿用 Vertex；官方 Code Review 設 Manual 模式，由驗收員通過後留言 `@claude review`；先試官方版一個月比較誤報率與成本；注意現有 `claude.yml` 只要留言含 `@claude` 就觸發，會與 `@claude review` 同時跑，要改 `trigger_phrase` 或在 `if` 排除。用通用正確性 review + `REVIEW.md` 寫系統不變量（`AllTools` 與 `tools.py`／`agent.py` 同步、`{content, sources}` 契約、`deploy.yml` 的 `envsubst` 白名單、改 agent／session／auth／部署要有 ADR、rumors-db mapping 升 `VERSION`、ES 不能用 `_id` 排序、url-resolver 新抓取路徑檢查 SSRF），風格交給 Prettier／ESLint／ruff。

**漏洞修補：** repo 與 lockfile 都公開，私有流程能爭取的是「發現到修好」的時間，讓公開的那一刻就是修補 PR。流程：開 Dependabot alerts、關 security updates PR → devops 每日排程 Action 把 high／critical alert 開成 devops issue（label `vuln`）→ Claude routine 評估影響、升級並跑測試、結果貼回 devops issue（**不 push branch 到公開 repo**）→ 人類加 `approved` → routine 在公開 repo 開中性標題 PR（`chore(deps): bump X`）、merge 後立即部署。重大事件用 devops incident issue template；自家程式碼漏洞（如 10/18 的 SSRF）用 GitHub repository security advisory 的私有 fork。

**用量與方案：** nonprofit Standard $8/席（約 Pro 1.25 倍，最少 2 席）；Premium $40/席（Standard 的 5 倍；$40 為使用者提供，待在 admin billing 確認，一般價 $20／$100）；extra usage 按 API 牌價（Opus 5.5 輸入 $4／輸出 $20、Sonnet 5.5 $2／$10 每百萬 token）。兩種席位差 $32。掛 routine 的人以每月約 30 個 PR、每 PR 跑 2 次粗估 $90–240（API 牌價），應用 $40 席位；其他開發者先用 $8 觀察一個月。官方 Code Review 扣組織 usage credits、另設上限；Vertex 上的 `claude.yml` 走 GCP 帳單。

**分階段：** 第 1–2 週補 CI（vitest+coverage、url-resolver Actions、media-manager PR 觸發、rumors-api coverage 設定與 schema snapshot、`buf breaking`、rumors-db VERSION 檢查、開 Dependabot alerts）；第 3–4 週補關鍵測試、Storybook 截圖比對（待 cofacts/ai#154 merge）、PR template「需求來源」、驗收員第一版（未登入 + Storybook）、devops alert 同步與評估 routine；第 5–8 週：staging 測試帳號與登入 smoke、官方 Code Review 試行、跨 repo 契約 job、依用量調整席位。

**待團隊決定：** (1) routine 掛在誰的帳號（或另設「Cofacts bot」席位）；(2) staging 與 production JWT 金鑰是否已分開；(3) 截圖放 orphan branch 還是 GCS；(4) 驗收員要不要能擋 merge（建議頭一個月只留言）；(5) 是否寫成 ADR（驗收員架構、預簽 JWT 登入）。

**註：** 成本數字為粗估，以第一個月實際用量為準；未列出任何金鑰、IP 或使用者資料。

## site-tw 10/13 改成 1GB RAM：成本與延遲

目前設定是 1 CPU、1Gi、`minScale=0`、`maxScale=5`、concurrency 80、cpu-throttling 開啟。

### 成本

資料來自 BigQuery `billing_export`。它只有整個專案的 Cloud Run 總額，沒有 per-service 的標籤，所以下面不是 site-tw 單獨的數字，不過 site-tw 佔絕大部分流量。

| 期間                                  | Cloud Run 日均（USD） | 記憶體       | CPU     | 網路        |
| ------------------------------------- | --------------------- | ------------ | ------- | ----------- |
| 10/1–10/12（扣掉 10/8 異常高點 3.69） | 約 1.8                | 約 0.08      | 約 1.5  | 約 0.19     |
| 10/14–10/20                           | 約 1.15               | 約 0.09–0.11 | 約 0.85 | 約 0.17     |
| 10/21–10/26（流量增加）               | 約 1.7                | 約 0.10–0.15 | 約 1.25 | 約 0.2–0.33 |

- **記憶體費用：** 從 10/13 起，只增加每天約 0.02–0.03 美元，一個月不到 1 美元。
- **總費用沒有上升：** 10/13 之後 CPU 計費明顯下降，是同期總額下降的主因，需求量也沒變。
- **推測原因：** 先前 512MB 可能發生 OOM、重啟與 cold start 連鎖，導致 CPU 時間浪費。這是推測，我沒有看 OOM log 驗證。
- **每個 request 的成本：** 前後約 15.6e-6 美元降到 11.6e-6（10/14–20），10/21–26 約 9.8e-6。這比單看總額更能反映改善。
- **10/21 起的上升：** 來自 request 量增加。site-tw 約 100k 增加到 165–190k/日，出站網路也同步上升，不是記憶體造成的。

### 延遲

資料來自 Cloud Monitoring。日界線是對齊查詢結束時間（約 18:00 台北），不是午夜，所以 10/13 前後會有半天誤差。

| 指標                 | 10/13 前（9/30–10/12 平均） | 10/13 後（10/14–10/26 平均） |
| -------------------- | --------------------------- | ---------------------------- |
| p50                  | 約 357ms                    | 約 272ms（−24%）             |
| p95                  | 約 1.75s                    | 約 1.0s（−43%）              |
| p99                  | 約 65s                      | 約 15s（−77%）               |
| 5xx / 日             | 約 130                      | 約 55                        |
| 平均 active instance | 約 2.1                      | 約 1.6                       |

- 改完後，延遲各分位都下降，5xx 也減少，instance 數變少。
- 在 10/21–23 流量增加約 70% 時，p95 只從約 1.0s 微升到約 1.1s。
- **p99 仍偏高：** 即使降到 10–20s，仍可能有長連線或 cold start。
- **cold start：** p95 startup latency 在前後都是約 4.5–6s，沒有改善，這部分與記憶體無關。

### 結論與建議

這次改動是淨賺：成本沒有上升，反而下降，延遲顯著改善。

1. 1GiB 在 p99 仍貼近上限（0.98），建議觀察 Cloud Run log 有沒有 `Memory limit exceeded`。
2. 如果要再降 p99 與 cold start，可考慮 `minScale=1`，代價約每月 5–10 美元。這個數字是估算，我沒有查 Cloud Run 現行單價。
3. 10/8 的總額 3.69 美元是約兩倍的異常高點，我沒有追查原因。同一天 5xx 與 request 量也偏高，可能與流量事件有關。
