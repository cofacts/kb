### 「內文好、出處糟」案例：a5e8351f、92371cf8

**結論：** 問題主張多數不是幻覺，而是出處搞丟。主張在 investigator 的回傳裡找得到，但 writer 掛上的網址並不支撐那句話。另外每個 session 各有 1–2 則是 writer 自己生的。問題主張一則都沒經過 verifier，卻全標 `verifier_confirmed: true`。

| 主張分類 | a5e8351f | 92371cf8 |
|---|---|---|
| A 有工具依據，出處正確 | 1 | 2 |
| **B 有工具依據，出處掛錯** | **5** | **8** |
| C 只在原文或使用者訊息裡 | 1 | 1 |
| D 任何工具都沒回傳過 | 1 | 2 |

**實例：**
- **[a5e8351f](https://langfuse.cofacts.tw/project/cmm0emerr0001qi07eugd0760/sessions/a5e8351f-c35d-4300-b436-c360086be214)：原文網址是 writer 自己編的。** `thinkingtaiwan.com/content/3094` 從沒出現在任何工具輸出裡，正確的是 `.net/3055`，使用者按了倒讚。
  - 唯一一次 verifier 呼叫中斷，沒有結果。
  - gate 擋了兩次，writer 把網址補進 `references` 就通過了。
- **[92371cf8](https://langfuse.cofacts.tw/project/cmm0emerr0001qi07eugd0760/sessions/92371cf8-b90c-4b2d-956f-3ed9b31b5984)：網址真的出現在工具回傳裡，但掛錯句子。** 例如「HIV 18%→0.27%」的 grounding 是 aidsmap，卻掛了疾管署 2008 年的報告，那份報告不可能有 2010 年的數據。
  - **D 類：**「每 1 美元省 7 美元法律與醫療支出」是 writer 自己生的，還算在 UN/WHO 頭上。
  - **上游就沒依據：**「AAP 正式反對校園篩檢」這句 investigator 有寫，但它的 grounding 並不支撐。

**根因：**
1. investigator 只回傳一段文字和一份 `sources[]`，沒說明哪句對應哪個網址（`grounding_supports` 沒傳給 writer），writer 只能猜。
2. `verifier_confirmed` 由 writer 自己填，gate 不比對 verifier 的實際結果。
3. 後續回合常常不叫 verifier 就直接改稿。

#### 既有提案與 PR 的盲點

| 失敗類型 | 本次案例 | [#144](https://github.com/cofacts/ai/issues/144) 網址須在 sources 裡 | [#118](https://github.com/cofacts/ai/pull/118) verifier 先抓頁面 |
|---|---|---|---|
| writer 編造網址 | thinkingtaiwan.com/3094 | ✅ | — |
| 真網址掛錯主張 | 13 則 B 類 | ❌ | ❌ |
| 主張沒經過 verifier | 兩個 session 的多數主張 | ❌ | ❌ |
| writer 或 investigator 自己生的主張 | D 類，加上 AAP、UN/WHO | ❌ | ❌ |
| verifier 讀不到頁面卻亂判 | 92371cf8 補救階段的 18:05、18:10 | — | ✅（PDF 除外） |

- **#144 的效果：** 在 a5e8351f 擋下 2/5，但聯集裡沒有正確網址，只能逼 writer 重查；在 92371cf8 擋下 0/5。實作時要做網址正規化，因為有 vertexaisearch 轉址。
- **#118 的效果：** 只在 verifier 有被叫、而且有跑完時才起作用；verifier 的 ✓ 也沒接到 gate。

#### 建議討論

1. **investigator 回傳「主張→網址」對應。** 把 `grounding_supports` 轉成逐句出處。
2. **`verifier_confirmed` 改由系統依 verifier 實際的 ✓ 判定。** 這就是 #144「後續」那一項，建議重新排優先序。
3. **#118 要和第 2 點搭配。** 它是讓 verifier 可靠的前提，單獨上線效果有限。
4. **#144 仍值得做。** 成本低，能擋編造的網址。
5. **以上動工都需要補 ADR。**

**結論**：剩下的零星失敗有兩個來源：(1) PM2 reload 時約 1 秒沒有任何 worker 在 listen（設定問題，可修）；(2) Cloudflare tunnel 的 QUIC 連線偶爾斷線重連（非 app 問題）。LINE console 錯誤變少主要是因為 9/28 起 reload 從每小時改為每 3 小時；#417 沒有處理到主因，#416 看起來有效。

**四個待確認事項**
- #417（SIGINT graceful shutdown）：已上線，10/1 02:16 UTC merge（`release/20261001`），prod container 10/1 04:26 UTC 重建後未再換。
- 錯誤是否下降：有，但主要是 reload 次數從每天 24 次降到 8 次；reload 每次約 2–4% 機率掉 1–2 個 webhook，#417 前後一樣。#417 上線後 5 天共 6 筆失敗：2 筆來自 reload、4 筆來自 tunnel 斷線。
- reload cron（目前每 3 小時，UTC :15）：先修 PM2 設定再決定頻率。
- 舊謎團：10/4、10/5 兩次無法用 reload 解釋的失敗，對得上 cloudflared tunnel 斷線重連。9/19–9/27 那波 499 仍無解（見下）。

**每日失敗（/callback 非 200，UTC）**：9/6–9/18 每天 0–3 筆；9/19 起 499 暴增（9/19 7、9/20 10、9/21 36、9/22 35、9/23 44、9/24 105、9/25 15、9/26 18、9/27 22），9/28 起降到 0–2。每天總請求約 1 萬。
事件：#416 於 9/26 08:21 UTC 上線、9/28 cron 改每 3 小時、#417 於 10/1 上線。403/405 為無關掃描流量，已排除。

**cloudflared 失敗原因（9/6–10/5，以事件計；#416 前→後）**
- reload 當下 `connection refused`（那一瞬間沒有 worker 在 listen）：10→3
- reload 當下 `connection reset by peer`（舊 worker 結束切斷 keep-alive）：4→1
- 平常時段 reset / `server closed idle connection` / broken pipe（keep-alive 逾時 race，#416 處理的問題）：5→0，#416 有效
- tunnel `Retrying connection`（QUIC 斷線）：#416 後 2 次

**reload 為什麼掉請求**（10/5 00:15 UTC 那次）：新 worker 00:15:02 啟動，PM2 標為 online；00:15:05 即停掉舊 worker 0、1（此時新 worker 尚未 listen）；00:15:08 停舊 worker 2，此時沒有任何 worker 在 listen，cloudflared 收到 `connection refused` ×2（即 LINE console JST 09:15:09 的 2 筆 502）；00:15:09 新 worker 才印出 `Listening port 5001`（啟動約 7 秒）。原因：`ecosystem.config.js` 沒設 `wait_ready`，PM2 只等預設 `listen_timeout`（3 秒）就認定就緒。修法是 [rumors-line-bot#418](https://github.com/cofacts/rumors-line-bot/pull/418)：`wait_ready: true`，在 `server.listen` callback 內 `process.send('ready')`，`listen_timeout` 拉到約 15 秒。#417 改的是舊 worker 關閉流程，對此無幫助（舊 worker 收 SIGINT 後 60–200ms 就結束，handler 不等 `server.close()`，Node 16 不會主動關閉閒置 keep-alive 連線，所以 `kill_timeout` 也沒用到）。

**tunnel 斷線**：cloudflared 與 Cloudflare 之間維持 4 條 QUIC 連線，其中一條逾時（`no recent network activity`）會重連，期間走該連線的請求失敗，約每 2–3 天一次（例：10/4 23:36 UTC 重連→502 ×2；10/5 07:48 UTC 兩條同時重連→request_timeout ×2）。目前 cloudflared 為 2026.3.0，log 建議升 2026.9.0。

**9/19–9/27 的 499 已知線索**：只有 line-bot 受影響（其他 host 的 499 平常就多）；與 tunnel 斷線、reload 的 :15 都對不上，集中在台灣晚上 21:00–01:00；Cloudflare 記到數百筆但 cloudflared 只有約 15 筆 `context canceled`；`/callback` 驗簽後直接回 200、處理為非同步，不應慢到讓 LINE 放棄；app image 3 月起沒換、9/28 除 cron 外無其他變動；#416 上線後仍持續到 9/27。與 cron 調整時間吻合，但 9/6–9/17 cron 也是每小時卻沒出現，尚無結論。下一步可查那幾晚 app event loop 是否被卡住或 LINE 平台是否異常。

**建議下一步**：①line-bot 合 #418（wait_ready）；②devops 升級 cloudflared 到 2026.9.0；③團隊確認 LINE webhook redelivery 是否開啟；④之後再處理：SIGINT handler 等 `server.close()` 並關閉閒置連線（Node 18+ `closeIdleConnections()`）、清 Apollo API key 失效造成的 401/406 log。
