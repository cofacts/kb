### StaleSessionError（[ai#204](https://github.com/cofacts/ai/issues/204)）與背景續跑

- 原因：run 進行中，有外部寫入動到同一個 session 的 state，ADK 的 stale check 就讓這一輪 run 失敗。外部寫入目前只有兩條路：
    - 改 session 名稱
    - 開第二個分頁，或按停止之後寫入 `lastOpenedAt`
- [ai#205](https://github.com/cofacts/ai/pull/205)：讓只改 state 的寫入不會中斷正在跑的 run。CI 綠，但不打算 merge
    - 它要靠 invocation id 的 `p-` 前綴，分辨寫入是 ADK PATCH route 從外部來的，還是 run 自己的 callback 寫的
    - `p-` 是 ADK 內部的實作細節，ADK 沒有承諾會維持，升級可能就失效
- 改走 [ai#197](https://github.com/cofacts/ai/pull/197)（Redis Streams 背景續跑）：run 進行中有 lock，期間的寫入會延後，改名會被拒絕
    - preview 上 5 個情境都測過：關掉分頁再打開、第二個分頁加入、按停止、run 中改名被拒、sub-agent
    - production 要先設 `REDIS_URL`（[rumors-deploy#47](https://github.com/cofacts/rumors-deploy/pull/47)），沒設的話會退回舊路徑，#204 照樣會發生
    - 以後新加的 state 寫入都要走 `write_state()`，要寫進 ADR
    - 另一個版本：[ai#213](https://github.com/cofacts/ai/pull/213) 背景續跑 BFF 版（draft）

### 影片 embedding 實驗 → 可以 backfill

報告：[影片 kNN 搜尋評估](https://claude.ai/artifact/B3y1hjw7Ez5wtfk2mhW5oY)

<details>
<summary>Artifact 內容摘要：影片 kNN 搜尋評估（2026-11-24）</summary>

> 原始 HTML 存檔：[artifacts/20261124-B3y1hjw7Ez5wtfk2mhW5oY.html](./artifacts/20261124-B3y1hjw7Ez5wtfk2mhW5oY.html)

**結論：** 影片可以和文字、圖片一起 backfill（聲音不算）。加 kNN 不會弄壞現有搜尋，還能多找回很多；但影片搜尋的 kNN 門檻要設 0.85，不能用 0.7。對應 rumors-api #388 / #411。

**實驗方法：**
- 用 public API 撈出全部 21,652 篇影片；共用同一則查核回應的影片視為同一則謠言（標準答案），只算不同檔案的（相同檔案用 hash 就找得到）。
- 用沒登入的 public API 做逐字稿全文檢索模擬現況，沒有寫入 production。
- 四組題目：沒有逐字稿（196 題，全部；逐字稿為空或只有「字幕由 Amara.org 提供」之類套話）、穩定組（50 題，現在第 1 名就對）、漏網組（50 題，有逐字稿但前 10 名找不到同組影片）、逐字稿很像組（50 對，Claude 看影格標註）。
- 直接呼叫 Vertex、與 production 相同設定算出 1,049 支影片的向量（只看前 80 秒），含 300 支隨機影片作無關對照；1,049 支只有 1 支失敗（只有聲音、沒有畫面的檔案）。

**現況分數：** hash 只有完全相同的檔案才命中（100 分）；逐字稿全文檢索分數無上限（常見 150–250）；kNN 為 (1 + cosine) ÷ 2，最高 1 分，所以不會改變已被逐字稿找到的順序，只會把沒找到但很像的影片接在後面。

**結果：**
- 沒有逐字稿 196 題：前 10 名找得到 69 → 174 題；第 1 名就對 29 → 132 題。
- 漏網組 50 題：前 10 名找回 33 題（最樂觀 39）。沒找回的 17 題中 11 題是同一支影片的其他複本排在前面（只是沒連到同一則回應），實際表現比數字好。
- 影片超過 80 秒也找得回來（沒有逐字稿、超過 80 秒的 46 題：7 → 41），只看前 80 秒沒有明顯損失。
- 穩定組 50 題全部維持第 1 名，門檻 0.7～0.96 都一樣。

**門檻 0.85 的原因：** 影片向量彼此很接近。cosine 範圍（p10～p90）：隨機兩支無關影片 0.63–0.76（中位數 0.694）、同組不同影片 0.77–0.91（中位數 0.840）、同一支影片 0.97–1.00（中位數 0.989）。

| 門檻 | 沒有逐字稿：前 10 名 | 漏網組：前 10 名 | 每次搜尋多出的不相干影片 |
|---|---|---|---|
| 0.70 | 174 | 33 | 100（每題都有） |
| 0.80 | 174 | 33 | 100（75% 的題目） |
| 0.85 | 174 | 33 | 多數 0（25% 的題目有） |
| 0.90 | 173 | 28 | 幾乎 0（4%） |

以 296 個查詢影片估計全庫 21,652 支，各 cosine 區間每題碰到的其他影片數與標準答案數：0.70–0.75 約 6,386 支（標準答案 0.02）、0.75–0.80 約 1,887 支（0.05）、0.80–0.85 約 274 支（0.13，相關比例約 0.05%，仍是隨機）、0.85–0.90 約 29 支（0.45，約 1.5%）、0.90–0.95 約 1 支（0.27，約 21%）、≥0.95 約 3.9 支（9.22，約 70%，多半是同一支影片沒連到同一則回應的複本）。kNN 只取最近 100 名（k=100），門檻 0.7 實際帶進的是「全庫最像的 100 支」，其 cosine 中位數約 0.82（p10 0.78、p90 0.88），所以 0.7 與 0.8 結果幾乎相同；要擋掉不相干影片需設 0.85 以上。門檻 0.7 也會讓影片搜尋每次碰到約 280 張圖片和數千篇文字，0.8 以上幾乎沒有；反過來 backfill 後，用文字或圖片搜尋幾乎碰不到影片（≥0.75 的影片只有 3–7 支），不影響文字與圖片搜尋。門檻是搜尋時帶的參數，不影響 backfill。

**費用與延遲：**
- 費用約 US$1,000（2.1 萬支影片，每支平均 3,836 tokens；單價為推估，需對照帳單）。後續盤點把平均改為 4,287 tokens（隨機 299 支，57% 超過 80 秒），見下方 backfill 盤點。
- 算一支影片向量約 16 秒（p95 39 秒），LINE bot 查新影片的搜尋時間從約 8.5 秒變成約 17 秒；已在資料庫裡的影片 backfill 後讀快取，不會變慢。

**未解：** 單價為推估；「不相干」只依是否共用回應判定，沒有逐一看畫面確認。

**注意：** 沒有查到 production ES，下面數量是 public API 加程式碼推得的**上限**；實際覆蓋率要在 production 主機上跑 `devops/workspace/backfill-preflight/es_preflight.py`（唯讀）。

**結論：**

- 時間：concurrency 5 約 39 小時（影片約 24 小時），concurrency 15 約 13 小時。

**要先修的問題：**
1. backfill 腳本沒有排除 AUDIO，會算 322 篇（≤US$4，違反 rumors-api#418）；`CreateMediaArticle` 對新的 AUDIO 也會算（10/30 之後 2 篇）。
2. `--reembed` 會重算 10/30～11/15 的媒體向量（約 500 個，約 US$6），因為當時快取 docId 沒有版本；建議 `--reembed` 只處理 TEXT 和回應。
