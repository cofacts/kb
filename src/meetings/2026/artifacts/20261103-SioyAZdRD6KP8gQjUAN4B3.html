cofacts/ai · 問題一：Harness · 2026-10-30

cofacts.ai Harness Agent

這份只談 ADK 背後的 agent 要怎麼取得 coding harness 等級的能力。背景執行和重連（問題二）另開 session 討論，這裡只在和工作區相關時才會提到。依據是 cofacts/ai 的程式碼，以及 google-adk 2.13、claude-agent-sdk 0.2.175 的原始碼。

2026-10-30 回測結論：現在不值得投入完整的 H1 或 H3。在 9/18 之後的正式流量裡，harness 明顯會改善結果的 turn 只有約 1%。倒讚的主因是出處錯配和捏造，那是 #144 和模型選擇的問題。harness 反而會讓受影響的 turn 變慢、變貴。詳見Langfuse 回測。下面的方案分析保留，等工作負載改變時再拿出來。

三個方案共用一半的工程。工作區目錄、fetch_to_workspace、路徑守門、環境變數清理、配額和清理機制，不管選哪個方案都要做，而且應該先做。

H3（維持 ADK LlmAgent，自己補工具）比想像中便宜。ADK 2.13 已經有實驗性的 EnvironmentToolset（Execute、ReadFile、WriteFile、EditFile），也有遠端沙箱、Skills 和 token 門檻 compaction。程式面大約要補 6 到 8 個工具和幾個 callback。真正追不上的是行為調校：工具描述、system prompt、compaction 品質、subagent 怎麼分工。這些 Claude Code 已經調得很好，H3 要靠 cofacts-ai-eval 一輪一輪迭代。

建議：先做共用元件，再用 eval 讓 H3 和 H1（Claude Agent SDK）比一場。單台 GCE 上，H3 不用每個 run 開一個 claude 子程序，Langfuse、串流、callbacks 也都能原封不動，維運上明顯比較輕。如果 eval 顯示 H1 的查核品質明顯較好，再切換到 H1。

查核工作需要 harness 的哪些能力

我們要的不是寫程式的能力，而是 coding harness 處理資料的那套方法。

工作區下載的網頁、PDF、CSV 和使用者上傳的檔案要先存下來，需要時才讀進 context，不要一開始就整份塞進去。
讀大檔能分段讀、用 grep 找關鍵字、讀 PDF 指定頁、看圖片。
計算對 CSV 做篩選、加總、比對，例如核對政府開放資料裡的數字。
分工多個 subagent 平行查不同的主張，共用同一個工作區。
長 run 的 context 管理中途壓縮 context，工具輸出太大時存成檔案，只回傳預覽。
可控的最終輸出維持 draft_factcheck_response 的 per-claim gate、{content, sources} 的形狀，以及 Langfuse trace 和讚、倒讚回饋。

三個方案

H1

HarnessAgent 接 Claude Agent SDK

品質上限高

自寫 BaseAgent 包住 ClaudeSDKClient，把 SDK 的訊息流翻成 ADK Event。ADK 自己的 AntigravityAgent 就是同樣的做法，可行性沒有疑慮。

flowchart LR
  A["ADK FastAPI"] --> H["HarnessAgent (BaseAgent)"]
  H -->|"stream-json over stdio"| C["claude 子程序"]
  C -->|"Vertex AI"| M["Claude"]
  C --> B["內建: Read Glob Grep Write Edit Agent TodoWrite"]
  C -.->|"in-process MCP"| T["Cofacts 工具 + fetch_to_workspace + draft_factcheck_response"]
  B --> WS[("session 工作區")]
  T --> WS

優點

  • Read（含 PDF 和圖片）、Grep、subagent、mid-run auto-compact、大輸出存檔，這些都已經調校好了。
  • 工具在 ADK 的 Python process 裡執行，token ContextVar 和 url-resolver 都能沿用。

缺點

  • 每個進行中的 run 要一個 claude 子程序，官方建議至少 1 GiB，單台 GCE 能同時跑的 run 數量有限。
  • 只能用 Claude。root 變成自訂 agent 之後，Langfuse 要重接，工具名稱要正規化，UI 要加顯示不認得的工具的方式。
  • investigator 和 verifier 的 Gemini grounding 要包成工具才能保留。
H2

HarnessAgent 接 ACP

之後再說

好處是能換 harness，但 in-process 工具、hooks、structured output 都過不了 ACP，工具要改成 HTTP MCP，transcript 也存在 harness 的本機。cofacts 的最終答案可以靠 draft_factcheck_response 這個工具，所以 structured output 的缺口影響不大。等 Cofacts MCP（rumors-api PR 389）上線之後，可以把 H2 加成 H1 的另一個後端。

H3

維持 ADK LlmAgent，自己補工具

新的備選，建議先試

把現在的 ai_writer 升級成 harness：加上 ADK 2.13 的 EnvironmentToolset，再補上缺的工具和守門 callback。agent tree、callbacks、Langfuse、前端都不用改。

flowchart LR
  A["ADK FastAPI"] --> W["ai_writer: LlmAgent (Claude 或 Gemini)"]
  W --> E["EnvironmentToolset: ReadFile WriteFile EditFile Execute"]
  W --> N["自補: Glob Grep ReadPdfPage ViewImage Todo fetch_to_workspace"]
  W --> S["subagent: AgentTool + 共用工作區"]
  W --> T["現有 Cofacts 工具 + draft_factcheck_response"]
  E --> ENV{"BaseEnvironment"}
  ENV --> L["LocalEnvironment (工作區目錄)"]
  ENV --> R["E2B / Daytona / OpenSandbox / Agent Engine"]
  L --> WS[("session 工作區")]
  N --> WS

優點

  • 沒有子程序，記憶體只比現在多一點，單台 GCE 的並行能力不受影響。
  • Langfuse、串流、AllTools 同步、所有 callbacks（citation、url-resolver 注入、media 注入）都原封不動。
  • 不綁模型：writer 可以用 Claude，investigator 繼續用 Gemini grounding，每個 agent 都能各自換模型。
  • 可以一個工具一個工具加，每加一個就用 eval 量一次效果。

缺點

  • 工具描述、system prompt、compaction、subagent 怎麼分工，都要自己調。這是持續性的工作，也是 Claude Code 最難追上的地方。
  • EnvironmentToolset 標示為 @experimental，ADK 升級時 API 可能會變。
  • 通用 subagent 的接線要自己做，見「Subagent 與 writer 分身」一章。
H4

HarnessAgent 接 managed agent（Claude 或 Gemini）

備案

harness 和 sandbox 都交給供應商代管。ADK 這邊寫一個 BaseAgent，負責建立遠端 session、送出訊息、追蹤對方的 event stream，再翻成 ADK Event。ADK 2.13 的 ManagedAgent（Gemini Interactions，background=True）可以當參考。

flowchart LR
  A["ADK FastAPI"] --> H["ManagedHarnessAgent (BaseAgent)"]
  H -->|"建立 session、送訊息、追 event stream"| MA["Claude Managed Agents 或 Gemini Managed Agents"]
  MA -->|"remote MCP: 公開 URL + OAuth"| MCP["Cofacts MCP server"]
  MA -.->|"custom tool 進入 requires_action"| H
  MA --> SB[("供應商的 sandbox、檔案系統、transcript")]

優點

  • 供應商有真正的 sandbox：Bash、寫檔、跑 Python 都比較安全，前面討論的 secret 外洩和 metadata server 問題都不存在。
  • 工作區由供應商保管，不吃我們 GCE 的磁碟，也不用每個 run 開一個子程序。
  • run 在伺服器端持續跑，瀏覽器斷線也不受影響。

缺點

  • 工具：只有兩條路。一是做成公開的 remote MCP（可以和 rumors-api PR 389 的 Cofacts MCP 合併），二是用 custom tool，讓 session 停在 requires_action，由我們的 process 回應結果。callbacks（citation、url-resolver 注入）都得改寫成工具。
  • Claude 版：在 GCP 上只能透過 Anthropic-managed（Marketplace）使用，Vertex 不支援。資料只能放 US 或 global，存在 Anthropic，沒有亞洲區。除了 token 費用，每 session-hour 另收 0.08 美元。目前是 beta。
  • Gemini 版：只能用 Gemini 模型，目前是 Public Preview。環境閒置 15 分鐘後會做快照，7 天後刪除，所以使用者隔幾天再追問時，工作區已經不在了。也沒有 session list API。
  • Langfuse 要從供應商的事件重建 trace。
H5

Pi Durable：用新的 Node 服務取代 ADK

不建議採用 設計參考

@earendil-works/pi-durable（2026-10-01 發表，MIT）是一個 TypeScript library。每次 model call 和 tool call 都是會 checkpoint 的 durable task；UI 看到的都是已經提交的狀態，client 用 watch() 接回。它的 CodingTools 提供 read、write、edit、bash，透過可以替換的 ExecutionEnv 執行（本機、虛擬或遠端）。

flowchart LR
  F["BFF"] -.->|"session list、events、上傳都要重新對接"| P["新 Node 服務: pi-durable + 自寫 HTTP/SSE"]
  P --> ST[("自寫 Postgres storage adapter")]
  P --> T["TS 重寫的 Cofacts 工具與 callbacks"]
  P --> EX["ExecutionEnv: 本機、虛擬或遠端"]
  P --> MD["Anthropic / Gemini / Vertex Gemini"]

優點

  • durability 和多人 attach 是內建的設計。工具可以用 replay: "safe" 宣告 crash 之後能不能自動重跑。
  • 工具就是純 TypeScript 的 defineTool()，執行環境可以替換，和 H3 的 BaseEnvironment 是同一種思路。
  • 支援多家模型供應商。

缺點

  • 要拿新的 Node 服務取代 ADK：BFF 和前端的對接要重寫，agent.py 的所有 callbacks 也要移植到 TypeScript。
  • README 寫著 Experimental，API 隨時會變，也沒有附測試。沒有 HTTP server，也沒有官方的 Postgres storage，只有 Vercel 的 reference 實作。
  • 沒有內建 web fetch，coding agent 也沒有 subagent、MCP 或權限系統。這些都要自己補，補的量不比 H3 少。
  • 不確定是否支援 Claude on Vertex。

值得借鏡的地方：可以替換的執行環境、在工具上標註 replay 是否安全，以及「先送快照、再送 delta」的接回方式。

「ADK 現成」欄是我在 google-adk 2.13 原始碼裡查到的。工作量是相對估計：小代表一個工具或 callback 的規模，中代表需要設計和測試，大代表會持續調校。

小結：程式部分大約是 glob、grep、read_pdf_pages、view_image、todo、fetch_to_workspace，加上一個計算工具，再加上路徑守門、大輸出落地兩個 callback，以及共用工作區的 subagent。其中 fetch_to_workspace、路徑守門、工作區本來就是共用元件，所以 H3 真正多出來的程式量不大。風險集中在最後那一列：要做出和 Claude Code 一樣好用的工具描述和 agent 行為，得靠 eval 反覆調整，沒有捷徑。

Subagent 與 writer 分身

這是 H1 和 H3 之間最明顯的取捨。Claude Code 的 subagent 已經蓋好了：主 agent 寫一段任務描述，派給通用的 subagent，它用同一套工具在同一個 cwd 裡工作，平行執行，進度會回報。ADK 有這些零件，但接線要自己做。

情境

一則網傳訊息常常有好幾個面向，例如數據、人物發言、圖片出處。writer 可以為每個面向派一個分身，各自主導 investigator 和 verifier 的迴圈，查完擬好該面向的段落，再由 writer 合稿。

交接契約

  • 結構化回傳：欄位包含 aspect、status（done 或 partial）、verdict、draft、claims、sources、open_questions、notes_path。其中 claims 的形狀對齊 draft_factcheck_response 的 claim_sources，sources 維持 investigator 的形狀，讓 writer 的 attach_citation 統一編號。
  • draft 只是素材：最終稿的語氣、長度、結構由 writer 統一寫。
  • 細節放檔案：筆記和證據放在 work/aspects/<n>/，只有面向之間互相矛盾、或要引用原文時，writer 才去讀。sources/ 由所有分身共用，以 URL hash 做快取，寫檔要先寫暫存檔再改名。
  • 衝突處理：兩個面向的結論矛盾時，writer 要回頭看證據，或自己再叫一次 verifier，不能直接拼接。

修改版 AgentTool：把子 session 存下來

現在 AgentTool.run_async 在 agent_tool.py:274 寫死了 InMemorySessionService()，子層跑完 event 就消失了。修改版只改三件事：

  1. 改用真正的 session service。子 session 開在同一個 Postgres 的 DatabaseSessionService 上。
  2. 用獨立的 app name。例如 cofacts_ai__sub，子 session 就不會出現在側欄。ADK 的 GET .../sessions/{id}（api_server.py:1703）不檢查 app 是否存在，前端可以直接用現有的 endpoint 讀。
  3. 在回傳裡帶 child_session_id。寫在工具程式產生的 function_response 裡，模型無法竄改。

好處

  • 點開就能看：工具卡片加「查看過程」，用現成的 convertAdkSessionToChatState 重播子 session。investigator 和 verifier 也換成這個版本的話，就是一棵可以逐層展開的樹。
  • 進行中也看得到：子 session 的非 partial event 一寫進資料庫就讀得到，前端輪詢就能看進度。
  • 不會搶寫父 session：子層寫自己的 session，不會觸發 StaleSessionError。
  • #144 的 gate 可以吃真實紀錄：走訪 writer 的 events 時，遇到 child_session_id 就載入子 session 遞迴收集 sources[]，來源集合的定義和 #144 一致。
  • 可以接續同一個子 session：分身回報 partial 時，下一次呼叫延續同一個子 session。
  • 不做分身也有用：套在現有的 investigator 和 verifier 上，使用者就看得到 verifier 讀了哪些頁面，除錯也不必翻 Langfuse。

要注意

  • 維護成本：run_async 約 200 行，session service 寫死在裡面，只能整段複製，ADK 升級時要跟著對齊。比較好的做法是發 PR 給 ADK，讓 AgentTool 能傳入 session_service。
  • state 複製：子 session 會複製一份父 state，持久化之後每個子 session 都存一份，要先過濾。
  • 刪除要連動：ADK 不會連帶刪子 session，BFF 要自己依 child_session_id 一併刪除，保存期限也要和父 session、工作區一致。
  • 資料量：investigator 回應裡的 grounding 和搜尋 widget HTML 很大，存檔前可以先拿掉。
  • 權限：子 session 用同一個 user_id 建立，BFF 讀的時候要確認它屬於同一個使用者。

建議：走 H3 的話，先不做 writer 分身。H3 的最小版先用現有的 investigator 和 verifier 加上工作區工具，分身留到 eval 顯示「多面向的訊息品質較差」時再做。順序是：

  1. #144 的 provenance gate（獨立追蹤）。實作時讓收集來源的函式能吃子 session，介面先留好。
  2. 持久化子 session 的 AgentTool，先套在 investigator 和 verifier 上，獨立帶來可見性。
  3. writer 分身與交接契約。

如果最後選 H1，分身可以直接用 Claude Code 的 Agent 工具，但 #144 的來源收集一樣要處理子層（事件帶 parent_tool_use_id）。

  • 關掉 WebFetch。依 claude-agent-sdk 的 WebFetchOutput schema，它回傳的是 result，也就是「把 prompt 套用在內容上」的小模型摘要，不會存檔。查核需要原文和能引用的來源，所以所有抓取都改走 fetch_to_workspace：存原文、記 URL 和 hash 到 manifest，正好接上 source-coverage gate 和 stage_archived_links。
  • fetch_to_workspace 要防 SSRF。直接下載時要擋私有 IP、link-local 和 169.254.169.254，否則 agent 可以叫它去讀 metadata server。走 url-resolver（Cloudflare browser）的那條路，抓取本來就在外部發生。

Shell 的三個等級

  1. 不開 shell（建議起步）。檔案只透過我們的工具進來，用 Read、Grep 和 PDF、圖片工具處理。filesystem 的好處大部分就已經拿到了。
  2. 專用的計算工具。例如唯讀的 DuckDB 查詢，關掉網路和工作區外的檔案存取。CSV 的篩選、加總、比對夠用，風險也可以控制。
  3. 真正的 shell，放在沙箱裡。
    • H1 可以用 Claude Code 的 bubblewrap。但在 docker 裡要打開 enableWeakerNestedSandbox，SDK 自己寫了這會降低安全性。
    • H3 可以把 BaseEnvironment 換成 E2B、Daytona、OpenSandbox，或另開一個不帶任何憑證、網路受限的 sandbox container。
    • 不管哪條路，shell 都應該不能連網，只計算本地檔案。

不論哪個等級，都要在 ADK 讀完 secrets 之後把它們從 os.environ 刪掉，或者用明確列出的 env 啟動子程序。

目錄配置

/var/lib/cofacts-ai/ws/{session_id}/ 底下分成 uploads/、sources/（附 manifest.json）、work/，H1 再多一個 .claude/。這個目錄要掛 host volume。清掉一個 session 就是刪掉一個目錄。H1 的 transcript 另外用 SessionStore 備份到 Postgres。

一直累積的後果

  • 單台 GCE 的磁碟滿了，整站一起倒。frontend、ADK、url-resolver、docker log 都在同一台，寫不進去就全部出錯，不只是查核功能。
  • 寫在 container 的 writable layer 會有兩個問題。平常它長在 /var/lib/docker 裡，不容易監控；redeploy 重建 container 時又會整批消失，使用者下次追問時檔案已經不見了。
  • Cloud Run 會 OOM。dev 和 preview 跑在 Cloud Run 上，它的可寫檔案系統就是記憶體，會吃掉 backend 的 2 GiB，OOM 時整個 instance 連同進行中的 run 一起被殺掉。
  • H1 的 transcript 也會長。Read 過的內容會以 tool_result 的形式寫進 transcript。另外 Claude Code 預設 cleanupPeriodDays: 30，transcript 如果只存在本機，30 天後再追問就 resume 不起來。
  • 隱私。使用者上傳的 LINE 截圖和轉傳訊息可能含個資，保存期限要和 Cofacts 的隱私政策一致。
  • context 不受影響。檔案放在磁碟上，只有被讀的時候才進 context，這正是要用 filesystem 的理由。

管理機制

  • 入口集中：檔案只能從 fetch_to_workspace 和受限的 Write 進來。設單檔上限、每個 session 的總量上限、content-type 白名單，由 after_tool callback 或 PostToolUse hook 記帳，超過就拒絕寫入。
  • 冷熱分層：本機只當快取，run 結束時同步到 GCS（可以放在現有 artifact bucket 底下），GCS 用 lifecycle rule 設保存期限。下次 run 時本機沒有就還原，或只還原 manifest，讓 agent 自己重抓。
  • 清理程式：session 閒置超過一段時間，或磁碟用量超過門檻時，依 LRU 刪本機目錄，但要跳過正在跑的 session。「哪些 run 正在跑」要從問題二的 run registry 取得，這是兩個 session 之間唯一的介面。
  • 產出檔案：只有要給使用者看的檔案（例如整理好的 CSV）才升級成 ADK artifact，UI 已經有讀 artifact 的路徑。

Langfuse 回測：換成 harness 會有什麼改變

資料來自 Langfuse 上的 1,275 個正式環境 turn（2026-03 到 10-30，production 與早期的 default 環境）和 377 筆讚、倒讚。延遲和成本是實際量測值。品質的影響是估計：由模型依固定評分表判讀 268 個 turn 的紀錄，判斷「同樣的模型加上工作區、全文抓取、Read、Grep 和共用工作區的 subagent，結果會不會明顯變好」。這 268 個包括全部 148 個倒讚，以及 120 個 8 到 10 月的隨機抽樣。它不是重播實驗。

速度與成本：受影響的 turn 會變慢、變貴

  • 最慢的環節是 investigator 和 verifier 的 Gemini grounding，harness 沒有改變這一段。
  • 判讀為「會變好」的 turn，多半估計要多走 4 到 10 步。以每步 p50 約 6 秒、約 0.01 到 0.03 美元推算，每個這種 turn 會多 25 到 60 秒、0.05 到 0.3 美元。H1 還要加上 claude 子程序的冷啟動時間（未實測）。
  • 多面向平行可以縮短時間，但不需要 harness：ADK 已經支援同一輪平行呼叫。現在有多次子 agent 呼叫的 turn 中，串行 456 個、平行 50 個，其中一部分是 investigator 到 verifier 本來就有的依賴，但仍然有用 prompt 就能挖的空間。
  • 如果讓 harness 在每個 turn 都多走幾步（coding harness 的常態），延遲和成本會全面上升，而 83% 的 turn 在品質上沒有收穫。

查核協作者會有感覺嗎

幾乎不會。大部分 turn 是短訊息、Cofacts 連結和改稿，harness 不會改變結果。會變好的情境（質疑引文、PDF 條文）一個月大概只有一兩次。反而是變慢比較容易被感覺到：現在 p90 已經 255 秒了。協作者最容易感受到的改善是「出處可以相信」（#144、換 writer 模型），以及「關掉頁面不會白等」（問題二的背景執行）。

建議：暫緩 H1 和 H3，把資源放在下面這些地方。

  1. #144 的 provenance gate，針對倒讚的第一大主因。
  2. writer 換 Sonnet 的完整流程 A/B（接 mrorz 的實驗）。
  3. 問題二的背景執行，改善「等待」的感受。
  4. 兩個小切片：「引文必須出現在 url-resolver 抓到的全文裡」的檢查，和給 verifier 用的 PDF 分頁工具。這也是 H3 共用元件的一部分，之後要做完整 harness 時不會白做。

什麼時候該重新評估：PDF、資料表類的任務明顯變多，或者 cofacts.ai 要支援跨多份文件的研究、長期研究這種新用途時。

這份回測的限制

  • 品質影響是模型讀紀錄後的判斷，不是重播實驗。判讀者讀的是壓縮過的 digest，四個判讀者之間也有尺度差異（各批「會變好」分別是 14、4、4、6 個）。
  • 9/18 之後只有 81 個樣本，「約 1%」的信賴區間很寬。
  • 「更長、更深入的研究」沒被使用者嘗試過，所以數據反映的是現有的使用方式，而不是 harness 可能帶來的新用途。
  • 如果要更紮實的證據，可以挑 10 到 15 個 9/18 之後、多面向或帶 PDF 的 turn 做重播實驗。

建議路線

  1. 共用元件。工作區目錄和 volume、fetch_to_workspace（含 manifest 和 SSRF 防護）、路徑守門、環境變數清理、配額，以及 GCS 同步和清理程式。這些和選哪個方案無關。
  2. H3 的最小版。在 ai_writer 上加 ReadFile（分段讀）、glob、grep、read_pdf_pages、view_image、todo，不開 shell，也先不做 writer 分身。用 cofacts-ai-eval 的 session replay 和現在的 writer 比較。
  3. H1 的 spike。用同一套工具和工作區，搭配同一組 eval 題目，量查核品質、延遲、成本、記憶體。
  4. 依 eval 結果決定。H1 明顯勝出，就把它接到 feature flag 後面，補 Langfuse 和 UI。差距不大，就繼續強化 H3，再視需要加計算工具或沙箱 shell。

依 CLAUDE.md，工作區、沙箱策略和 agent 編排的變更都屬於應該寫成 decision record 的範圍。

尚未驗證

  • ADK token 門檻 compaction 在單一長 run 中途的實際行為與摘要品質。
  • EnvironmentToolset 能不能依 session 切換工作區（toolset 是在 agent 定義時就建好的）。
  • claude 子程序在 GCE 上實際的 RSS 和冷啟動時間。
  • bubblewrap 在 cofacts 的 docker 設定下能不能啟用。
