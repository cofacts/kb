cofacts/aicofacts/rumors-apicofacts/rumors-dbcofacts/url-resolvercofacts/media-managercofacts/devops

目標是讓 PR 在人類看之前，已經跑過測試、看過畫面、對過需求，也做過 review。下面的建議分成兩層：確定性的檢查放在 repo 裡的 GitHub Actions（便宜、可重現、能擋 merge），需要判斷的驗收交給一個跨 repo 的 Claude「驗收員」（讀需求、操作 preview、截圖、提出修復路徑），review 排在驗收員之後啟動。

  1. 先補 CI 的洞，再談 AI。 cofacts/ai 的 CI 沒有跑 vitest（87 個前端測試只在本機跑）；url-resolver 只有 .travis.yml，PR 上沒有任何測試；media-manager 只在 push 時跑。這三個都是一兩行 workflow 就能補的。另外 rumors-api 與 ai 之間的 GraphQL schema 目前完全沒有契約檢查。
  2. Coverage 用「變更行覆蓋率」當門檻，不設全域門檻。 全域數字落差太大（adk 77%、前端 20%），設門檻只會逼人寫無意義的測試。新增或修改的行要求 ≥ 80%，不需要測的檔案在設定檔排除。
  3. 驗收員用 Claude Code 排程任務（routine），由 CI／Deploy 完成後呼叫 API 觸發。 它能一次 clone 多個 repo，適合跨 repo 的需求；需求來源讀 PR 連結的 issue、GitHub Project、kb 會議記錄與 design doc。
  4. 登入問題用 staging 專用測試帳號 + 預先簽好的 session JWT 解決，Playwright 直接把 cofacts_session cookie 塞進瀏覽器，不走 OAuth 頁面。前提是 staging 與 production 的 JWT 金鑰不同。
  5. Code review 沿用 Vertex AI billing，不要用個人 subscription 的 OAuth token：官方文件明講共用的 CI secret 應該用 API key／雲端帳號，個人 token 綁在單一使用者的額度上。
  6. 漏洞修補在私有的 cofacts/devops 開票、評估、測試，人類加 label 放行後才在公開 repo 開 PR。 需要另一個能讀 Dependabot alerts 的 GitHub App 或 token，因為 Claude GitHub App 沒有這個權限。
  7. 方案：先全員 $8 nonprofit Standard 席位 + 開 extra usage 並設上限，跑一個月看每人的 extra usage。 超過 $32/月的人（主要是掛 routine 的那位）升級成 $40 席位。

PR 自動驗證

單元測試回答「這個函式對不對」，驗收要回答「這個 PR 有沒有做到它說要做的事、有沒有弄壞別的地方」。後者需要讀需求、操作實際部署、看畫面，這部分交給 Claude。

整體流程

PR 開啟或更新repo 自己的 CI 跑測試、coverage、契約檢查（見下節）。cofacts/ai 同時部署 preview（含 /storybook/）。
Deploy／CI 成功後呼叫驗收員workflow 最後一步 curl 驗收員 routine 的 /fire endpoint，帶上 repo、PR 編號、preview URL。這樣驗收員一定在部署完成後才開始，不必輪詢。
驗收員蒐集需求PR 內文與 Closes #N 連結的 issue、GitHub Project（AI 相關是 org project 12）、cofacts/kb 的會議記錄與 design doc（src/meetings/、src/technical-design/）、repo 的 docs/decisions/。
驗收員實際操作用 Playwright 開 preview：未登入頁面、Storybook 上這次改到的元件、登入後的聊天流程（見下方登入方案），逐條對照需求截圖。
回報在 PR 上維護一則置頂留言（每次更新同一則），內容是需求對照表、截圖、失敗項目與建議修法。
啟動 code review驗收通過後才觸發 review（見 Code review）。

需求來源

驗收員可靠的程度取決於能不能找到需求。建議依序找：

  1. PR 內文的「需求來源」欄位：加一個 PR template，請作者貼 issue、會議記錄段落或 design doc 的連結。最便宜，也最準。
  2. 連結的 issue（Closes #N）與它在 GitHub Project 上的欄位。
  3. kb 會議記錄：會議記錄裡大量直接引用 PR 編號（例如 10/20 那份提到 #118、#154、#162、#163），而且每份都有 OKF frontmatter。驗收員可以直接 grep -rn "ai/pull/162\|#162" src/meetings/ 找出討論脈絡與決議（例如「#162 為了 Claude on Vertex 把附件濾掉了，不確定是不是真的不能吃檔案」，這就是驗收時要確認的一條）。
  4. design doc 與 ADR：kb 的 src/technical-design/、src/research/，以及 repo 內的 docs/decisions/。

找不到需求時，驗收員應該在留言裡明說「沒找到需求來源，以下只做 regression 檢查」，不要自己腦補需求。

登入怎麼做

cofacts.ai 的 session 就是 HttpOnly cookie cofacts_session，內容是 rumors-api 用 RS256 簽的 access JWT（token_use: "access"，效期等於 COOKIE_MAXAGE，預設 14 天）。BFF 只驗證簽章，不在乎 cookie 是怎麼來的。所以自動化不需要走 OAuth 畫面：

  1. 在 staging 資料庫建一個專用測試帳號（例如 cofacts-ai-e2e），權限跟一般使用者一樣。
  2. 在 rumors-api 加一個小腳本，用 staging 的 JWT_PRIVATE_KEY 呼叫既有的 signLongLivedJWT(userId) 簽出 token，由人工執行，存進 cloud environment 的 network secret（給驗收員 routine 用）或 GitHub secret（給 Playwright workflow 用）。
  3. Playwright 用 context.addCookies([{ name: 'cofacts_session', value, domain: '<preview host>', path: '/', httpOnly: true, secure: true, sameSite: 'Lax' }])，接著直接開頁面。
  4. 14 天會過期：腳本可以加 --ttl 參數，只替測試帳號簽 90 天的 token；或者每兩週由人工重簽一次。
前提：先確認 staging 與 production 的 JWT_PRIVATE_KEY 不同。若相同，staging 簽出的 token 在 production 也有效，這個方案就不能用，要先分開金鑰。另外不建議在 preview 加「測試用登入 route」，那段程式碼遲早會跟著 image 進 production。
Session DB。 ADK 的 staging DB 已經與 production 分開（DB 名稱加上 staging 後綴，#163 已 merge）。production 在 GCE 上用 rumors-deploy 的 env file，與 Cloud Run 的 DATABASE_URL secret 無關。preview 與 staging 仍是同一個 Cloud Run service、同一個 DB，所以驗收員建立的 session 會留在 staging DB。用專用測試帳號就能辨識，必要時依 user id 定期清掉即可。

截圖怎麼貼到 GitHub

GitHub CLI v2.99.0（2026-09-01）起，gh pr comment、gh issue comment 和 create / edit 都支援 --attach，檔案會上傳到 user-attachments 並插入內文，一次最多 50 個，需要 repo 的 push 權限。要確認的只有執行環境的 gh 版本：

  • 推薦：gh pr comment <N> --body-file report.md --attach shots/login.png --attach shots/chat.png。body 裡已經寫的 ![alt](./shots/login.png) 會被原地換成上傳後的網址。GitHub Actions runner 與 routine 的 cloud environment 都要先把 gh 升到 2.99 以上（我這個 cloud session 裡是 2.89，沒有這個參數），routine 可以在 environment 的 setup script 裡裝。
  • 沒有新版 gh 時的備案：同 repo 開一個 orphan branch pr-screenshots，路徑 pr-<N>/<sha>/*.png，留言用 raw URL 嵌入。
  • GCS bucket（設 30 天 lifecycle）：圖片不進 git 歷史，但要多管一個 bucket 與權限。
  • Actions artifact：只能下載，不能在留言內顯示，不適合。

Regression：不重複既有測試

驗收員不應該重跑 CI 已經跑過的單元測試，而是做 CI 做不到的事：

  • 視覺差異：Storybook 上每個 story，在 staging 和 preview 各截一張比對，只回報有差異的。
  • 端到端 smoke：固定 3–5 段對話腳本（例如一則有圖片的可疑訊息、一則帶連結的訊息），確認 preview 能跑完、回應有 sources、引用的網址真的出現在工具輸出裡。最後這條檢查跟 #144 的程式層級出處檢查是同一個方向。
  • agent 品質：改到 adk/ 的 prompt 或模型時，抽 cofacts-ai-eval（#143）裡的小樣本跑一次，報分數變化。整套 eval 太貴，不適合每個 PR 都跑。
  • 整合測試：rumors-api 的雲端整合測試已經在每晚的 integration.yml 跑。驗收員只需要在 PR 改到那些模組時，提醒「這個 PR 影響的整合測試只在 nightly 跑」，必要時用 workflow_dispatch 手動觸發一次。

結論：契約檢查放 repo 層級，功能驗收放 routine。 跨 repo 的功能（例如 rumors-api 加欄位、ai 使用它）由驗收員處理：rumors-api 沒有 preview 環境，驗收員能做的是確認兩邊的 PR 互相引用、契約檢查都通過，然後在 ai 的 preview 上（指向 staging API）驗證。真正的端到端要等 rumors-api 的 PR 部署到 staging 之後；驗收員可以在 ai 的 PR 留言列出「等 rumors-api#N 上 staging 後要補驗的項目」。

建議

  • 計費沿用 Vertex，不用個人 subscription。 官方文件對 org 共用的 secret 建議用 API key 或雲端帳號，因為 OAuth token 綁在跑 claude setup-token 那個人的 subscription 上。用個人 token 等於把團隊的 CI 額度跟某人的日常使用綁在一起，那個人離開或額度用完時 review 就停。
  • 「驗完功能才 review」的做法：官方 Code Review 設成 Manual 模式，由驗收員在通過後留言 @claude review。routine 以掛的人的身分留言，那個人有 write 權限，所以這個留言有效。若用 Action 版本，就用 workflow_run 接在 CI 與 Deploy 之後。
  • 先試官方 Code Review 一個月（Manual 模式、設每月上限），跟目前的 Vertex 方案比較誤報率與成本。注意：現有 claude.yml 只要留言含 @claude 就會觸發，跟 @claude review 會同時跑；要嘛把 claude.yml 的 trigger_phrase 改掉，要嘛在 if 排除 @claude review。

通用 review 還是放入團隊偏好？

用通用的正確性 review，再補上足夠的脈絡；不要一開始就寫風格偏好。格式與風格交給 Prettier、ESLint、ruff。脈絡放在 REVIEW.md，內容是這個系統特有、而且出錯代價高的不變量，例如：

  • src/lib/adk.ts 的 AllTools 必須與 adk/cofacts_ai/tools.py、agent.py 同步。
  • {content, sources} JSON 契約與每條主張的出處覆蓋檢查。
  • deploy.yml 的 envsubst 白名單：新增 placeholder 卻沒加進清單，會原封不動送進 Cloud Run。
  • 改到 agent 編排、session 儲存、auth、部署時，要有 docs/decisions/ 的 ADR（呼應 CLAUDE.md 的規則）。
  • rumors-db mapping 有變要升 VERSION；ES 查詢不能用 _id 排序（ES 9 遷移的經驗）。
  • url-resolver 會依使用者提供的網址發出請求，任何新的抓取路徑都要檢查 SSRF（10/18 會議發現 url-resolver 與 ES 在同一個網路）。

之後 review 裡反覆出現的團隊意見，再逐條加進 REVIEW.md。

漏洞修補

先說清楚能隱藏什麼

這幾個 repo 都公開，package-lock.json、pnpm-lock.yaml、uv.lock 也都公開。任何人都能從 lockfile 看出套件版本，再對照公開的 advisory。所以私有流程真正能爭取的是從發現到修好的時間：Renovate 或 Dependabot security PR 一開，就等於公告「這裡有洞、還沒修」，而且這個訊號一直掛到 merge 為止。私有流程讓公開的那一刻就是修補 PR 本身，最好連部署也在同一天完成。

dependabot high / critical 的流程

開啟 Dependabot alerts，關閉 Dependabot security updates只要 alert（只有 repo 管理者看得到），不要它自動開公開 PR。
devops 每日同步 alertcofacts/devops 裡一個排程 GitHub Action，用一個有 Dependabot alerts: read 權限的 GitHub App 或 fine-grained token，把各 repo 新出現的 high / critical alert 開成 devops issue（label vuln，用 alert URL 去重）。Claude GitHub App 的權限清單沒有 Dependabot alerts，所以這一步不能靠它。
Claude 評估影響一個 routine 以 GitHub trigger 監聽 devops 的 issues.opened（label vuln）：clone 受影響的 repo，判斷有沒有實際用到有漏洞的程式路徑、是不是只有 devDependency，然後在 session 裡升級套件、跑測試，把影響評估與 diff 貼回 devops issue。不要 push branch 到公開 repo，branch 名稱本身就會洩漏。
人類放行維護者看完評估，加上 label approved。
開公開 PR同一個 routine 監聽 issues.labeled，在公開 repo 開 PR。標題用中性的 chore(deps): bump X，merge 後立即部署，最後關閉 devops issue。

rumors-api 與 url-resolver 的 Renovate（每月一次）可以保留，負責一般升版；安全性升級走上面這條。在 Renovate 設定把有 advisory 的套件交給上面的流程處理，避免兩邊重複開 PR。

重大事件（on-demand）

  • 在 devops 加一個 incident issue template（時間軸、影響範圍、處置、後續）。發現事件的人開票，在 claude.ai/code 以 devops + 受影響 repo 開 session 處理。
  • 解完才對外說明：在 devops issue 寫好摘要，由人工貼到 Slack（若 routine 接了 Slack connector，可以讓它草擬，由人按送出）。
  • 不是依賴套件、而是自己程式碼的漏洞（例如 10/18 的 SSRF），用 GitHub 的 repository security advisory：它提供暫時性的私有 fork 讓人在裡面修，修完再一起公開。公開 repo 免費。
