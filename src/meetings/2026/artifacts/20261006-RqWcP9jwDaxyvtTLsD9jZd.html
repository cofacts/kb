reload 為什麼會掉請求

10/5 00:15 那次 reload 的時間線（PM2 與 app log）：

UTC發生什麼
00:15:02.1新 worker 0、1 啟動，PM2 標示為 online
00:15:05.13 秒後 PM2 就停掉舊 worker 0、1。此時新 worker 還沒開始 listen，只剩舊 worker 2 在接請求
00:15:08.4PM2 停掉舊 worker 2。此時沒有任何 worker 在 listen
00:15:08–09cloudflared 收到 connection refused ×2，也就是 LINE console 上 JST 09:15:09 的那 2 筆 502
00:15:09.1新 worker 終於印出 Listening port 5001，距離啟動約 7 秒

app 啟動到開始 listen 大約要 7 秒，但 ecosystem.config.js 沒有設定 wait_ready。PM2 只等預設的 listen_timeout（3 秒）就認定新 worker 已就緒，開始停舊的。修法（#418）是設定 wait_ready: true，在 server.listen 的 callback 裡 process.send('ready')，並把 listen_timeout 拉到 15 秒左右。

#417 改的是舊 worker 的關閉流程，對這個問題沒有幫助。而且舊 worker 收到 SIGINT 後 60–200ms 就結束（handler 沒有等 server.close()，Node 16 也不會主動關閉閒置的 keep-alive 連線），所以 kill_timeout 也沒有用到。reset 這類失敗目前很少，可以晚點再處理。

tunnel 斷線

cloudflared 和 Cloudflare 之間維持 4 條 QUIC 連線。其中一條逾時（no recent network activity）後會重連，期間走那條連線的請求就會失敗。這個月大約每 2–3 天發生一次。

LINE console（JST）cloudflared（UTC）結果
10/5 08:3610/4 23:36:07 重連，23:36:19 恢復502 ×2
10/5 16:4810/5 07:48:38 兩條同時重連，07:49:07 恢復request_timeout ×2

目前跑的 cloudflared 是 2026.3.0，log 一直提示建議升到 2026.9.0。升版不一定能消除斷線，但成本低，值得先做。

9/19–9/27 的 499，目前已知

  1. 只有 line-bot 受影響。其他 host 的 499 平常就多（瀏覽器關分頁），同期沒有明顯增加。
  2. 和 tunnel 斷線時間對不上，也不集中在 reload 的 :15。主要出現在台灣晚上 21:00–01:00。
  3. Cloudflare 記到數百筆，cloudflared 只留下約 15 筆 context canceled。大部分請求在 cloudflared 那邊沒有錯誤紀錄。
  4. /callback 驗完簽章後就直接回 200，處理是非同步的，所以正常情況下不應該慢到讓 LINE 放棄。
  5. app image 從 3 月起沒換過。這波 499 在 #416 上線（9/26）後仍持續到 9/27，9/28 起消失。9/28 只改了 cron，沒有其他變動。

和 cron 調整的時間吻合，但 9/6–9/17 cron 也是每小時，當時沒有出現，所以還不能下結論。下一步可以看那幾個晚上 app 的 event loop 是否被卡住，或是 LINE 平台那段時間是否有異常。

建議下一步

line-bot

PM2 加上 wait_ready（已開 PR：cofacts/rumors-line-bot#418）：在 server.listen 的 callback 裡送 process.send('ready')，listen_timeout 設 15 秒。這可以處理目前 reload 失敗的大部分。

devops

升級 cloudflared，從 2026.3.0 升到 2026.9.0。

團隊

確認 LINE 的 webhook redelivery 有沒有開。有開的話，tunnel 斷線這類短暫失敗會自動重送，影響就很小。

line-bot

之後再處理：SIGINT handler 改成等 server.close() 完成並關閉閒置連線（Node 18 以上有 closeIdleConnections()）。Apollo API key 失效造成的 401／406 log 也順手清掉。
