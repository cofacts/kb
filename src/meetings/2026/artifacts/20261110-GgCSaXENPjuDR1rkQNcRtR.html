Widen the Funnel 工作項目

nDX 這次想做的，是用設計讓查詢訊息的人，變成回應訊息的人。三條核心工作線落在漏斗最後一段「產生貢獻」；第四條只做產品內的引導。每條工作線列出設計要交付什麼、工程要接什麼，以及它靠哪些現有工作。

漏斗出處：CCPRIP · Project WTF 平台：Phase 3 網站遷移與前端架構

範圍

這份包含
  • cofacts.ai 對話介面的資訊整理（訪談後優化）
  • /report 的導引與送出後的流程
  • 讓查核協作者回來貢獻的機制與通知
  • AI agent 對使用者的導引（產品內的部分）
這份不含
  • 網站遷移本身（Phase 3 Track 0–6，已有專案看板）
  • 社群貼文、LINE 推播等行銷內容製作
  • AI 爬蟲放行與能見度（devops）
  • 預算與科目配置

哪些項目放在這份、哪些移到別的專案，是我依對話整理的判斷。有放錯的請直接指出。

工作項目

核心產生貢獻

Acofacts.ai 對話介面的資訊整理

AI agent 的英文 thinking、「」包起來的 tool call 和說明文字全部一起出來，畫面太亂，使用者看不出哪裡是草稿、哪裡是佐證。先和資料建置小組訪談，再依結果最佳化。

設計
  • 訪談：問資料建置小組實際怎麼用、哪些內容會看、哪些直接略過。
  • 重排資訊層次的 Penpot 稿：思考過程、工具呼叫、草稿、佐證各自的呈現與收合方式。
  • 手機版與長對話的狀態。
工程
  • 把串流事件分類：哪些是思考、工具呼叫、最終說明、草稿。
  • 依新稿實作，元件放進 Storybook。
  • 英文 thinking 的處理方式（隱藏、收合或翻譯）要工程評估可行性與成本。
靠
  • Phase 3 Track 5　AI chat：/ai、/ai/session/:sessionId、工具抽屜，Penpot 已有稿，這項是在它之上的優化。
  • Penpot 到程式的規則：token 名稱直接對應 class（cofacts/ai#176）。
狀態
Track 5 尚未看到認領者。這項要等訪談結果，再決定是否與 Track 5 合併處理。
衡量
訪談前後的使用者回饋；對話中產出可送出回應的比例。間接支撐 KR 1-2、KR 2-1。
核心前段加分認知問題使用平台產生貢獻

B/report 的導引與流程

新的 /report 已經在做。這一項是它之後的最佳化：讓使用者容易把訊息送進來，送出之後自然被引導去協助查核，而不是結束就離開。

設計
  • 送出完成後的畫面：下一步是什麼（看相似訊息的回應、協助補充線索、請求優先查核）。
  • 導流頁與分享出去的預覽卡片視覺。
  • 抓不到內文時，請使用者改傳截圖的流程。
  • 「遇到就來回報」的說明文案與位置。
工程
  • 手機分享選單的接收：/report?url=&text=&title= 已定義，Android 分享選單直達在 #139。
  • iOS 沒有 Web Share Target，需評估用「捷徑」的做法。
  • 送出後的下一步，依賴相似訊息搜尋（見工作線 C 的依賴）。
靠
  • Phase 3 Track 3　回報可疑訊息：Penpot 的 AI 頁已有 6 個狀態板。
  • cofacts/ai#138、#139 review 中；#148（抓不到內文時改上傳截圖）。
  • 設計上已決定：回報走獨立流程，不放進 AI 對話裡，避免回報者分心（20260910）。
衡量
從 /report 送出到有人寫出回應的轉換（KR 1-2）。前兩段的認知與使用屬加分。
核心產生貢獻

C讓查核協作者回來貢獻

人進來之後，要有理由回來。三個想法：定時挑出 low-hanging fruit 給他們；告訴他們「你寫的回應有 N 人覺得有幫助」（像 Google Maps 告訴評論者評論的影響力）；找出不讓人覺得煩的聯繫方式。訪談對象也在 nDX 專案裡，可以在專案期間直接驗證。

設計
  • 通知與任務的體驗：收到什麼、多久一次、點進去看到什麼。
  • 「回應有幫助」訊息的文字與呈現，用訪談測試哪種說法有效。
  • 任務清單頁（或任務卡片）的版型。
  • 讓協作者控制頻率與關閉的設定。
工程
  • 定時挑選候選訊息：已查過的相似訊息、尚未回應。
  • 排除不適合的訊息：只有網址的文章（占文字文章 34%）、FB 分享連結只拿到登入牆的。
  • 通知管道與排程；先手動或半自動產生清單給小組試用，再自動化。
  • 正評數據的取得，供影響力通知使用。
前例
  • WTF 第 4 段：每週感謝、每半年再邀請來過的人。
  • 2017 的 filter：只有一則回應、我沒回過。
  • 2023 ChatGPT 構想：標出哪些需要回應。
  • X 的 Request a Note：請求累積到門檻，推給高貢獻撰寫者。
依賴
  • vector search（相似訊息搜尋）：rumors-api#411 在 staging 驗證中。
  • 9.4% 的相似度查詢命中內容真的相似且已有回應的文章（20260922），候選池夠不夠大要先量。
  • 「我送出的訊息」filter 已有票（rumors-site#631）。
注意
資料建置小組是寫過 400 篇以上回應的資深協作者，這裡驗證的是「回鍋」；新手轉換（KR 3-1）要靠工作坊的參與者。
衡量
回鍋人數、回應數（KR 1-2）、正評數（KR 2-1）。
加分使用平台產生貢獻

DAI agent 的導引

使用者自己的 AI agent 查 Cofacts 時，除了回答，也能告訴使用者「這則還沒有人回應，可以到 /report 回報，或自己來查核」。只做產品內與 MCP 的部分，不設指標。

設計
  • 導向 /report 與查核的落地頁文字，要讓 agent 容易轉述。
工程
  • MCP server 的 instructions 與 prompts：引導 agent 先查相似訊息，再導向 /report 或自行查證。
  • 文章頁加給 AI 讀的說明（尚未回應時的行動指引）。
靠
Cofacts MCP Server 設計文件「待討論」已提到這個方向。
限制
MCP 的安裝門檻高，目標使用者是已有自己查核流程的人，覆蓋面有限。

順序與依賴

先做A＋C 合併訪談訪談對象是資料建置小組。一次問兩件事：對話介面怎麼用、什麼情況下會回來。
接著C 的清單試跑先手動或半自動產生 low-hanging fruit 清單給小組，觀察有沒有人回來寫。
並行B 接在 /report 之後#138、#139 合併後，再排送出後的流程與導流視覺。
有餘裕D不設指標，用現有的 MCP 與文章頁小步試。

需要設計師與工程師決定的事

  1. A 要和 Track 5 合併，還是獨立做？Track 5 還沒有人認領，訪談結果出來前不用急著決定。
  2. 英文 thinking 怎麼處理？隱藏、收合或翻譯，各自的實作成本，請工程評估。
  3. C 的任務清單放在哪？獨立頁面、站內通知，還是 LINE 或 Discord 的推送。這決定設計要做多少頁，也決定工程要接哪些管道。
  4. iOS 的分享入口要不要做？Android 在 #139 已有做法，iOS 需要另外的方案。
  5. B 送出後的「下一步」有哪些選項？設計先列候選，工程確認哪些資料現在拿得到。
