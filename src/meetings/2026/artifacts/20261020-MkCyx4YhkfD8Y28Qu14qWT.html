COFACTS.AI 出處品質｜下週討論用

維基百科來源評級，能幫 Cofacts.ai 挑出處嗎？

把 Cofacts.ai 近五個月實際用過的出處，拿去比對中文維基《來源評級/列表》與英文 WP:RSP，看列表涵蓋多少、評級回傳給 writer 之後可能改變什麼。

資料期間 2026-05-13 – 2026-10-13 來源 Langfuse traces 維基快照 2026-10-13 ADK 1.26.0
第一部分研究：列表命中度與影響 第二部分技術討論：怎麼接進 agent 流程
第一部分

研究

結論

  • 中文列表命中約 四成出處（草稿 41%）。英文列表只再多 2–3 個百分點，可以晚點再做。
  • 最大的影響是維基百科本身：23% 的草稿引用維基，而兩個列表都把維基評為「通常不可靠」。
  • 約一半的命中落在「依主題分評級」的條目，而且分歧點正好是政治報導。只回傳基準評級會誤導，必須回傳摘要讓模型依主題判斷。
  • writer 現在已經會避開「應停用」來源（入選率 5%），所以評級對這類來源的邊際效果不大。
  • 沒被列表涵蓋的約 56%，大宗是政府網站、查核組織、學術期刊，需要另訂規則。

影響一

草稿大量引用維基百科

176 / 765草稿引用了維基百科（23%）
193個逐項主張以維基頁面為佐證（claim_sources）
239筆 references 指向 zh / en / ja 維基

維基百科本身並非可靠來源，因為開放維基是個人出版物……經驗不足的編者有時可能會無意中引用關於某個出版物的維基百科條目，而不是該出版物本身；在這種情況下，應修正引用，而不是刪除它。

中文維基《來源評級/列表/維基百科》，評級 通常不可靠（WP:CIRCULAR）

維基條目通常附有原始出處。回傳評級後，writer 比較可能改引條目背後的報導或文件，這是這次評估中最直接、量也最大的改變。

影響二

評級依主題而定，政治報導最常被降級

中文列表 363 筆中有 86 筆在摘要裡依主題給出不同評級。Cofacts.ai 的命中有一半落在這類條目（investigator 52%、verifier 54%、草稿 45%）。台灣主流媒體的分歧點幾乎都是政治報導，也就是 Cofacts 訊息的大宗。

英文列表

英文 WP:RSP 值得接嗎

英文列表 497 筆。它的 13% 命中大多和中文列表重疊，主要也是維基、Facebook、YouTube。只有英文列表才命中的出處，在草稿中佔 2.8%，其中「通常可靠」1.8%，包括 Guardian、Reuters、SCMP、海峽時報、Al Jazeera、JAMA。

它的優點是結構整齊：依主題分評級時直接拆成多列，例如 Fox News 的政治與非政治分開，不用解析內文。適合當國際媒體的補充，優先順序可以放後面。

內容上要決定的事

  1. 維基百科出處怎麼處理？

    只提示、要求改引原始出處，或由 draft_factcheck_response 驗證時擋下。

  2. 如何區分「佐證」和「說法的出處」？

    FB、YouTube、官媒在 Cofacts 常是被查核的對象，提示內容需要能表達這個差別。

  3. 未列來源的備援規則

    政府網站、查核組織、學術期刊、轉載平台各自怎麼處理。

  4. 要不要接英文列表？

    增量約 2.8 個百分點，以國際媒體為主。

方法與限制

這份數字怎麼來的

  • 出處取自 Langfuse 的 TOOL observation：investigator 與 verifier 取輸出的 sources[].url，草稿取 draft_factcheck_response 輸入的 references。
  • 中文列表逐頁讀取《Wikipedia:來源評級/列表/*》共 363 / 364 頁，只缺「看中國」（持續被限流）。基準評級取 infobox 的 status，主題評級取摘要中的 {{通常不可靠}}、{{RSNG|…}} 等模板。
  • 網址比對採網域或其子網域；條目若宣告了路徑（例如 facebook.com/taipeibo），則要求網址路徑也相符。
  • 入選率以同一 trace 內的 URL 完全比對計算，同一則報導若換了網址形式（例如加了追蹤參數）會被算成未入選。
  • 從雲端 IP 呼叫 MediaWiki API 會被回 429，這次改用 action=raw 慢速抓取。正式同步需要固定主機與帶聯絡資訊的 User-Agent。

其他做法

Design alternatives

B離線先寫好提示，callback 直接附上

每週同步時，用模型一次把每個條目的摘要壓成「主題 → 評級 → 一句提示」，例如「政治：通常不可靠｜其他：半可靠」。執行時由現有的 append_grounding_sources / append_url_context_sources 查表附上，判斷主題的工作交給 writer。

優點 不改 agent 結構，不增加執行時的模型呼叫，延遲為零，也最好測試。

缺點 writer 要自己對照主題；每個命中的來源都會附上提示，writer 的 context 會變長。

C在 writer 的 after_tool_callback 裡呼叫便宜模型

不包成 SequentialAgent，而是在 _normalized_response 之後直接呼叫 rater 模型（genai client 或 Claude client），合併回 tool result。

優點 工具名稱、測試、引用機制都不用動；同一輪的多個工具結果可以合併成一次 rater 呼叫。

缺點 rater 不是 ADK agent，Langfuse 上要手動加 span；callback 裡呼叫模型比較不直觀。

D交給 verifier 自己判斷

verifier 本來就逐項判斷主張，request 裡也有主張原文。用 before_model_callback 把 request 中 URL 的評級注入，由 verifier 在報告中直接說明。

優點 不增加 agent 或模型呼叫。verifier 手上有主張原文，也讀過頁面內容，看得出是政治新聞、評論專欄還是官方帳號，判斷主題的條件最好。進入草稿的 claim_sources 都要求 verifier_confirmed，所以實際被引用的來源都會經過這一關。

缺點 「內容是否支持主張」和「來源是否可信」要分開輸出，否則 verifier 可能把有支持但來源弱的主張打 ✗，連帶讓「誰說過」這類合理引用被丟掉。investigator 階段沒有提示，writer 可能先拿弱來源跑一輪 verifier 才知道要換。提示寫在報告文字裡，較難統計和強制。另外 verifier_confirmed 是 writer 自己填的布林值，覆蓋率取決於 writer 有沒有真的呼叫 verifier。

Ewriter 主動查詢的工具

新增 check_source_reliability(urls) function tool，由 writer 自己決定何時查。

優點 實作最簡單，只在需要時花 token。

缺點 writer 可能不查；多一輪工具呼叫。

F草稿送出時的硬性檢查

在 draft_factcheck_response 的驗證中加規則，例如 claim_sources 若指向維基百科，就退回並要求改引原始出處。

優點 確定會生效，可以和其他任何方案疊加。

缺點 只適合規則明確的情況，處理不了依主題判斷的評級。

方案執行時多的模型呼叫依主題判斷結構變動trace 可見度

一種分階段的路線

先做 B + F。B 的離線提示本來就是 A 和 C 也需要的資料，F 直接處理量最大的維基引用。上線後用 Langfuse 觀察兩項指標：草稿引用維基的比例，以及政治類主張只靠「政治報導通常不可靠」來源佐證的比例。如果 writer 常套錯主題，再升級到 A 或 C，B 的資料可以沿用為 rater 的輸入。A 和 C 之間的取捨，在於 trace 是否清楚、結構變動能否接受。

另一條同樣不需要新模型的路線是 D + F：由 verifier 依主張判斷評級，F 擋下維基引用。前提是 verifier 的報告把「是否支持」和「來源可信度」分成兩欄。investigator 階段可以再用 B 的查表結果附上簡短提示，減少 writer 拿弱來源去驗證的來回。

技術面待決

架構上要決定的事

  1. 評級在哪一段加入？

    A 包裝成 SequentialAgent、B 在現有 callback 查表、C 在 writer callback 呼叫 rater，或分階段進行。

  2. 依主題的判斷由誰做？

    rater 小模型、writer，或 verifier。
