cofacts.ai 背景續跑

讓 cofacts.ai 的 AI 查核助理在使用者關掉瀏覽器後繼續完成工作，重新打開時接回最新進度；同一個對話開在兩個視窗時，兩邊都能看到即時輸出。這頁說明現況為什麼做不到、打算怎麼改，以及用 Redis Streams 當 run registry 的細部設計。

背景：今天的 run 怎麼跑

cofacts.ai 是 Cofacts 的 AI 查核助理。使用者貼上一則可疑訊息，agent 會搜尋 Cofacts 資料庫和網路、核對來源，最後寫出一份附來源的查核回應。一次問答在系統裡叫一個 turn，執行一個 turn 的過程叫一個 run；同一串對話叫一個 session。

flowchart LR
  B["瀏覽器"] -->|"POST /api/run-sse"| F["BFF (TanStack Start)"]
  F -->|"POST /run_sse, 轉傳 request.signal"| A["ADK FastAPI (get_fast_api_app)"]
  A --> W["ai_writer: Claude Haiku on Vertex"]
  W -->|"AgentTool"| I["investigator, verifier: Gemini"]
  W -->|"tools"| T["搜尋 Cofacts 資料庫、起草回應等"]
  A --> PG[("Postgres: ADK sessions")]
  A --> G[("GCS: 上傳檔案")]
  • 元件：前端和 BFF 是 TanStack Start；後端是 Google ADK（Python）的 FastAPI server，session 存在 Postgres。
  • 部署：production 是 GCE 上 docker compose 裡的 adk 與 cofacts-ai 兩個容器，ADK 只跑一個 uvicorn process。dev.cofacts.ai 和 PR preview 是 Cloud Run 上的多容器 service，最多 3 個 instance。
  • 一個 turn 會跑很久：主 agent 會呼叫做網路搜尋的子 agent，單一次模型呼叫曾跑到 195 秒，Cloud Run 的 request timeout 因此調到 900 秒。
  • 串流方式：瀏覽器送出問題後開著一條 SSE 連線，ADK 的 /run_sse 一邊執行一邊把事件推回來。事件分兩種：partial 是逐字打出的文字片段，只用來即時顯示，不會存檔；非 partial 是完整的訊息、工具呼叫和工具結果，寫進 Postgres 後才送出。

問題：run 的壽命綁在 HTTP 連線上

使用者關掉分頁、手機切到背景太久，或網路斷線，瀏覽器的 fetch 就會中斷。BFF 把這個中斷（request.signal）轉傳給 ADK，ADK 接著取消整個 run。從 ADK 2.11 起，/run_sse 在 client 斷線時一定會中止 run，沒有選項可以關閉（google/adk-python issue #4029 仍開著）。

斷線後留下什麼已經寫進 DB 的非 partial event 會保留；正在打的字全部遺失；ADK 另外補一筆 INVOCATION_ABORTED。使用者回來只看到一半的過程，沒有答案。
ADK 的 resume 幫不上忙前端有寫好但沒用到的 resumeRun(invocationId)。實測用 ADK 的 resume 接續被中斷的 turn，模型看到的工具結果是「Invocation was aborted」，不會接著把工作做完。
同一個 session 開兩個視窗今天沒有任何機制讓第二個視窗看到第一個視窗正在跑的內容，只能等跑完後重新整理。

做法：把「執行 run」和「觀看 run」分開

  • 不用 ADK 內建的 /run_sse，改在 adk/main.py 自己建一個 Runner（沿用同一組 Postgres 和 GCS 服務），加上自訂的 HTTP route。
  • 送出問題時，用 asyncio.create_task 在背景啟動 run，不依附在任何 HTTP 請求上。瀏覽器斷線只會少一個觀看者，run 照常跑完。
  • run 的每個事件寫進一個 Redis Stream，這就是 run registry。任何視窗都可以隨時接上：先補送 stream 裡這個 run 目前為止的事件，再阻塞等待後續事件。
  • 停止鈕改成呼叫一個 cancel API，由 server 取消 run，不再靠中斷連線。

run registry 直接放在 Redis Streams，和 rumors-line-bot 共用既有的 Redis。

  • 不用自己寫通知機制。寫入端 XADD；SSE handler 用 XREAD BLOCK 等新事件。接上時先用 XRANGE 補送這個 run 目前為止的事件，再從最後一筆的 ID 接著 XREAD，中間不會漏也不會重複。慢的 client 只是讀得慢，不需要踢人的規則。
  • 不用新增基礎設施。production 的 GCE 上已經有 redis 容器，和 adk 在同一個 docker network。staging 的 LINE bot 連的是 Redis Cloud 上的免費機器，Cloud Run 的 dev 和 preview 可以連同一台。
  • 比放在 ADK process 記憶體多三個好處。Cloud Run 不必限制成只有一個 instance。owner 掛掉時鎖會自動過期，正在看的 client 馬上知道 run 中斷了。之後要開多個 uvicorn worker 時，設計不用改。
  • Redis 救不了 run 本身。跑 run 的 ADK process 掛掉，run 就斷了。redeploy 時收到 SIGTERM 就立刻取消所有進行中的 run，把已打出的字補寫進 Postgres，前端顯示「中斷了」和重問按鈕。

多個 client：執行中的 client 各自讀同一個 stream，turn 結束時 server 關閉連線，client 就變成靜態。靜態的 client 不 polling，只在「載入頁面、分頁重新變成可見、自己要送出」這三個時機查一次狀態。

要先處理一個現有程式的衝突：打開 session 時，前端會寫入 lastOpenedAt。這會讓正在跑的 run 死於 StaleSessionError，所以 run 進行中要先跳過這次寫入。

Redis 裡放什麼

先定義兩個下面會一直用到的詞：

  • drain task：POST /runs 用 asyncio.create_task 開的那個背景工作。ADK 的 runner.run_async() 是一個 async generator，要有人一筆一筆把事件拉出來，agent 才會往下跑。今天負責拉的是 /run_sse 的 HTTP 請求，所以請求一斷，run 就停了。改成由 drain task 拉：它把事件一路拉到結束（drain，抽乾），每拉到一筆就寫進 Redis，和有沒有人在看無關。
  • owner：這個 drain task 所在的 ADK process。production 只有一個 ADK process，所以永遠是它；在 Cloud Run 上則是收到 POST /runs 的那一個 instance。只有 owner 記憶體裡有這個 task，所以只有它能直接取消 run、替鎖續約；它掛掉，run 就跟著中斷。鎖的內容會記下誰是 owner。

SSE handler 不碰 runner，只讀 Redis，所以它們可以在任何一個 ADK process，甚至不同的 Cloud Run instance 上。

為什麼鎖和 stream 是兩個 key

stream 只在 run 進行中有用。run 一結束，所有事件都已經在 Postgres，新接上的 client 用 session API 就拿得到完整歷史。網路正常時，handler 都停在 XREAD BLOCK，事件一寫進來就讀走並送出，讀到 done 時 stream 已經沒用了。寫入 done 後還留 30 秒，是給網路慢的 client：handler 讀到事件後要等 yield 把 bytes 送出去，client 收得慢時，send 會被 TCP 回壓卡住（例如手機在弱訊號下收一大段補送的事件）。這段時間新的 entry 在 Redis 裡排隊，等 handler 回到下一次 XREAD 才讀。如果排隊期間 stream 就被刪掉，它會漏掉最後幾筆和 done 標記。落後超過 30 秒的話一樣會發生：handler 等到逾時、發現鎖不在，就直接關閉連線，client 照「連線結束」的規則查狀態、重抓歷史，畫面一樣正確。

鎖還是要獨立一個 key。「一個 session 只能有一個 run」要靠 SET NX 原子地保證，stream 沒有「不存在才建立」的指令。鎖的 TTL 只有 30 秒，owner 掛掉後很快就會消失。

中斷之後怎麼知道中斷了。一律看歷史，不靠 Redis。正在看的 client 會先遇到連線被關掉（handler 發現鎖不見了），接著照「連線結束」的規則查狀態、重抓歷史，結果和之後才打開的 client 一樣：

  • 按停止或收到 SIGTERM 時，補寫的那筆 event 會在 customMetadata 記下 cancelled 或 interrupted。
  • process 直接當掉、來不及補寫時，歷史的最後一筆不會是 writer 的回答。

這兩種情況，前端都顯示「中斷了」和重問按鈕。

stream 用 session 當 key，handler 只靠 session id 就找得到，不必先讀鎖。代價是同一個 session 的下一個 run 會重用同一個 key（owner 當掉留下的 stream 最多再活 60 秒），所以每筆 entry 都帶 invocationId，handler 只看鎖裡那個 run 的 entry。這樣就算 handler 剛好在新 run 取得鎖、還沒 DEL 舊 stream 的瞬間讀到舊內容，也不會混進來。

寫入端：owner 的 drain task

  • 每個事件（partial 和非 partial 都算）append 一筆到 stream。
  • 寫入不在 drain 迴圈裡逐筆 await：事件先放進 process 內的緩衝區，由 writer task 每 50 ms 用一個 pipeline 批次 XADD。在 GCE 上連本機的 Redis 時，這樣做沒有差別；但 Cloud Run 連 Redis Cloud 要走網際網路，逐筆等來回時間的話，上千個 partial 會把整個 turn 拖慢好幾秒到幾十秒。
  • run 結束時先把緩衝區寫完，再寫一筆 done 標記（handler 看到就關閉連線），最後刪鎖。
async def drain(run, agen):
    try:
        async for ev in agen:
            run.writer.put(entry(ev))        # writer task 每 50 ms 以 pipeline 批次 XADD
        status = "completed"
    except asyncio.CancelledError:
        await salvage_partial(run)           # 已打出的字補寫成非 partial event（ADK 2.13 實測可行）
        status = "cancelled"
    except Exception:
        status = "failed"
    finally:
        await run.writer.flush()
        await r.xadd(run.stream_key, {"type": "done", "data": status})
        await r.expire(run.stream_key, 30)   # 只留給還沒讀完的 handler
        await release_lock(run)              # 比對 owner 後才刪，避免刪到別人的鎖

接上時為什麼從頭補送，不用 Last-Event-ID 續傳

Redis Stream 的 ID 本身就能拿來做 Last-Event-ID 續傳，但我們不需要：一個 run 從頭到尾都留在 stream 裡，接上時一律從這個 run 的開頭補送最簡單。補送的就是一般的 data: frame，handler 把它們串成一個 chunk、一次 yield。為了少送一點，已經有完整版的 partial 可以略過，只留最後一則還在打的訊息的 partial。client 接上時先清掉快取裡屬於這個 run 的事件，之後收到的全部照順序套用。重連、換裝置、第一次打開都走同一條路。

SSE handler 怎麼知道有新事件

handler 停在 XREAD BLOCK，直到 stream 有新的一筆，或者 20 秒逾時才返回。逾時就送一行 heartbeat，並確認鎖還在。這不是 polling：等待發生在 Redis 端，ADK 這邊沒事件時不佔 CPU。

@app.get("/runs/{sid}/stream")
async def stream(sid: str, user_id: str = Depends(bff_user)):
    async def gen():
        lock = await read_lock(user_id, sid)
        if lock is None:
            return                                           # 沒有在跑：直接關閉連線
        inv = lock.invocation_id
        key = stream_key(user_id, sid)
        raw = await r.xrange(key)                            # 目前全部
        mine = [e for e in raw if e.invocation_id == inv]    # 只看這個 run 的 entry
        if any(is_done(e) for e in mine):
            return                                           # 剛好已經結束，歷史裡都有了
        backlog = [sse_event(e.data) for e in compact(mine)]
        if backlog:
            yield b"".join(backlog)                          # 補送：一次送出很多個 data: frame
        last = raw[-1].id if raw else "0-0"
        while True:
            res = await r.xread({key: last}, block=20_000)   # 有新事件或 20 秒後才返回
            if not res:
                if not await lock_held(user_id, sid, inv):
                    return                                   # owner 掛了，或落後太多沒讀到 done
                yield b": heartbeat\n\n"; continue
            for e in entries_of(res):
                last = e.id
                if e.invocation_id != inv:
                    continue
                if is_done(e):
                    return                                   # run 結束：關閉連線
                yield sse_event(e.data)
    return StreamingResponse(gen(), media_type="text/event-stream")
  • 不漏也不重複：XRANGE 讀到的最後一個 ID 就是 XREAD 的起點。這兩步之間 owner 寫入的事件 ID 一定比較大，會在下一次 XREAD 讀到。
  • client 斷線：Starlette 會 cancel 這個 generator，XREAD 被打斷。沒有訂閱名單要清，因為讀到哪裡只存在這個 handler 的區域變數裡。
  • 連線數：XREAD BLOCK 等待期間會佔住一條 Redis 連線，所以同時在看的 client 有幾個，就要幾條連線。連線池上限要依此設定；Redis Cloud 免費方案的連線上限也要先查（見下節）。

和 rumors-line-bot 共用要守的規則

  • 所有 key 都加 cofacts-ai: 前綴。line-bot 直接用 LINE userId 當 key 存對話狀態（redis.set(userId, context)），Bull queue 用 bull: 開頭，前綴不會撞到。用前綴而不用 DB 編號區隔，是因為 Redis Cloud 不一定支援多個 DB。
  • 每個 key 都要會過期。GCE 上的 Redis 沒有 maxmemory，我們漏設 TTL 就會一直長，而這台 VM 還跑著 heap 16 GB 的 Elasticsearch。stream 另外加 MAXLEN ~ 20000 當保險。
  • 程式裡不用 KEYS、FLUSHDB。要找某個使用者正在跑的 run（每人並行上限），用 SCAN MATCH cofacts-ai:run:{userId}:*。
  • 兩邊都能承受 Redis 重啟。Redis 沒有持久化：重啟時 line-bot 會忘掉使用者的對話狀態，我們這邊則是正在跑的 run 失去鎖和 stream。owner 續約時發現鎖不見，就重新取得鎖，從下一個事件繼續寫；這時在看的 client 會被斷線，重連後從 Postgres 的歷史接回。

Redis Cloud 免費方案要先查的事

  • 容量上限：一個 run 在 stream 裡大約幾百 KB 到 1 MB，結束 30 秒後就刪掉。staging 同時只有個位數的 run，應該放得下，但要扣掉 line-bot 已經在用的量。
  • 連線上限：每個在看的 client 佔一條連線，再加上 owner 寫入、續約各用的連線，以及 line-bot 自己的連線。
  • 所在區域：Cloud Run 在 asia-east1。離得越遠，批次寫入能省下的時間越多，這就是 writer task 要批次寫的原因。

如果免費方案放不下，退路是在 Cloud Run service 加一個 redis:alpine sidecar 並設 maxScale 1，程式不用改，只換 REDIS_URL。

redeploy 時直接取消所有 run

production 每次 redeploy 都會殺掉 ADK process。收到 SIGTERM 時不等 run 跑完，直接：

  1. 拒絕新的 run（回 503）。
  2. cancel 這個 process 上所有的 drain task。
  3. 每個 run 都把已打出的字補寫進 Postgres，並在這筆 event 的 customMetadata 記下 interrupted（之後打開的 client 靠它知道要顯示重問按鈕）。然後寫入 done 標記、刪鎖，正在看的 client 會看到連線結束。

這些只是幾筆 DB 和 Redis 寫入，幾秒內就做得完，docker compose 預設 10 秒的 stop_grace_period 和 Cloud Run 給的 10 秒都夠，不用調長。用 interrupted 而不是 cancelled，是為了讓前端分得出「使用者自己按停止」和「系統中斷」，後者要顯示重問按鈕。代價是 redeploy 當下正在跑的 turn 要請使用者重問；部署通常在流量低時進行，影響的 run 不多。

這樣能撐多少人

先把「人」換成同時進行中的 run 數。用 Little's law 估算：同時 run 數 ≈ 每秒新 turn 數 × 平均 turn 長度。以下數字只是示範用的假設：尖峰每小時 300 個 turn、平均 90 秒，同時大約 7.5 個 run。真實數字可以從 Langfuse trace 的起訖時間算出來。

registry 不是瓶頸

runner 還是在同一個 ADK process、同一個 event loop 裡跑，和今天的 /run_sse 一樣，所以容量上限和今天差不多，取決於下表的資源。真正的差別是：今天關掉分頁會順便取消 run，等於替系統卸載；改成背景續跑後，被放著不管的 run 也會跑完。所以要加上 run 長度上限和每人並行上限。

事件怎麼送到前端

全部都是一般的 data: frame，格式和今天的 /run_sse 一樣，前端的 parser 和 applyEventToState 都不用改。一條 stream 在線上長這樣：

data: {…這個 run 的使用者訊息…}

data: {…writer 的工具呼叫…}

data: {…工具結果…}

data: {"invocationId":"e-7f3…","author":"ai_writer","partial":true,"content":{"role":"model","parts":[{"text":"根據"}]}}

（以上是接上時一次補送的部分，以下是直播）

data: {…下一個 ADK Event…}

: heartbeat

data: {…writer 的最終回答…}

（run 結束，server 關閉連線）
  • 序列化：寫進 Redis 的 data 就是 ADK /run_sse 送出的同一種 JSON（camelCase 欄位，省略空值），handler 不用再轉換，前端看到的形狀和今天一模一樣。
  • 補送：一次 yield 可以包含很多個 frame，前端的 parser 本來就是用空行切 frame（chatCache.ts:139-148），不用改。舊的 /api/run-sse 和新的 stream 共用同一個 parser。
  • 順序：每個 handler 依 stream ID 的順序送出，和 owner 寫入的順序相同。BFF 只轉發 bytes，沿用 withHeartbeat 只在 frame 邊界插 heartbeat 的邏輯。

為什麼 partial 要原樣重播，不能只送累積好的文字

前端處理串流的方式是「接尾巴」：

  • partial 事件是增量，前端把它接在最後一則仍在串流的訊息後面（chatCache.ts:403-436）。
  • 完整的非 partial 訊息到達時，如果最後一則還在串流，前端不讀它的文字，只補上工具呼叫並標記完成（chatCache.ts:386-400）。

所以中途接上的 client 只要漏掉前面的 partial，這則訊息就會一直缺開頭，直到重新整理。partial 裡還可能有工具呼叫、多個 text part，或不同 author 的片段，與其讓 server 重做一次前端的合併規則，不如把這些 partial 原樣重播，結果就和從頭看到尾的 client 完全相同。一則長回答的 partial 可能有上千筆、約一兩百 KB，而且只在接上時送一次。

補送的事件怎麼和已載入的歷史合併

歷史一律用 ADK 內建的 session API（GET /apps/{app}/users/{user}/sessions/{id}，前端今天就在用），不另寫 API。合併只有一條規則：正在跑的那個 invocation 只信 stream，其他 invocation 只信歷史。所以歷史和 stream 誰先到都沒關係，前端也不用逐筆去重（前端訊息的 id 是自己產生的 genId()，本來就沒存 ADK event id）：

  1. 快取除了算好的畫面狀態，另外存一份原始的非 partial ADK events。畫面本來就是從 events 算出來的（convertAdkSessionToChatState）。
  2. 接上 stream 時（invocationId 從 status、202 或 409 的回應得知）：從原始 events 拿掉這個 invocation 的事件並重算畫面，之後 stream 送來的事件全部照順序套用。歷史如果比較晚回來，也先濾掉這個 invocation 的事件。
  3. 收到一般的非 partial 事件：加進原始 events，照舊 applyEventToState。
  4. 連線結束：見下一段。

為什麼補送還要包含非 partial 事件？這些事件確實早就在 Postgres，內建的 session API 拿得到。但拿歷史和接上 stream 是兩個不同時間點的請求，Postgres 和 Redis 又不是同時寫入（先寫 Postgres，最多晚 50 ms 才寫 Redis）。如果只補送 partial，就得靠「歷史最後一筆」和「stream 的位置」對齊：歷史拿得太早會漏掉中間幾筆完整訊息；拿得太晚，則會先看到完整訊息、又疊上同一則訊息的 partial，變成重複。從這個 run 的開頭補送、整段替換，就不用處理這些競態。代價是接上時重送一次這個 run 的工具結果，大約幾百 KB。之後若嫌多，可以讓 client 帶上它歷史裡最後一筆 event id，server 只送那之後的部分。

自己送出問題時樂觀加上的使用者訊息，也會在接上 stream、清掉這個 invocation 的事件時，被 server 補送的正式版本取代。

連線結束時

不送專門的結束事件：run 結束時，server 在最後一筆事件之後關閉連線；連線還在，就表示還有事件。但連線也可能因為網路斷掉（手機換網路、Cloudflare 斷線），而且可能剛好斷在一筆完整事件之後，所以 client 不能只憑「斷在哪裡」判斷，規則是：

  • 最後一筆是 writer 的最終回答（非 partial、沒有工具呼叫），或是停止、中斷時補寫的訊息（customMetadata 標記 cancelled 或 interrupted）：不用查，直接變成靜態、刷新側欄。標記 interrupted 的顯示重問按鈕。
  • 其他情況（斷在 partial、工具呼叫或工具結果之後）：查一次 GET /runs/{sid}/status。還在跑就重新接上，會再補送一次；沒在跑就重抓歷史，最後一筆不是最終回答時顯示「中斷了」和重問按鈕。

這等於把今天 startChatStream 的 finally 擴充成「判斷要不要重接」。

邊界情況

情況會發生什麼處理方式
打開 session 時寫入 lastOpenedAt每次打開 session，前端都會 PATCH session state（session.$sessionId.tsx:76、chatSessions.functions.ts:183-203）。如果 run 正在跑，下一次 append 就會丟 StaleSessionError，run 直接死掉。背景續跑之後，「run 進行中打開 session」會變成常見的路徑改打 POST /sessions/{sid}/opened：鎖存在就不寫，回 deferred；client 在連線結束後再呼叫一次
owner process 當掉run 中斷，已寫入 Postgres 的 event 保留；正在打、還沒完成的那則訊息遺失鎖 30 秒內過期。handler 發現鎖不見就關閉連線，正在看的 client 查狀態、重抓歷史；之後才打開的 client 也是看歷史。歷史的最後一筆不是 writer 的回答，所以都顯示「中斷了」和重問按鈕
redeploy同上SIGTERM 時立刻取消所有 run、補寫已打出的字、補寫的訊息標記 interrupted 後關閉連線；前端顯示「中斷了」和重問按鈕
Redis 重啟鎖和 stream 都消失（line-bot 的對話狀態也一樣）owner 續約時重新取得鎖並繼續寫；在看的 client 斷線後從 Postgres 歷史接回，這個 run 之前的 partial 會看不到
Redis 連不上無法取得鎖POST /runs 回 503，前端退回舊的 /api/run-sse（過渡期保留）
沒人看的 run 一直跑今天關分頁會取消，以後不會owner 在 15 分鐘時自行 cancel 並補寫（和 Cloud Run 現在的 900 秒一致）
一個人同時開很多 session 跑今天沒有任何速率或並行限制啟動前 SCAN 這個使用者的鎖，超過 2 到 3 個就回 429
JWTtoken 存在 ContextVar；create_task 會複製當下的 context，middleware 之後 reset 的是原 request 的 context，不影響 task建立 task 時仍明確把 token 帶進去比較清楚。JWT 有效期 14 天，run 期間過期的機率可以忽略
權限stream 和 cancel 只帶 session id鎖和 stream 的 key 都包含 userId，由 BFF 解析後帶入，別人猜到 session id 也接不上
Cloud Run 的 CPU預設只在處理請求時配置 CPU，回應結束後背景的 run 會被限速設 run.googleapis.com/cpu-throttling: "false"；scale-in 時 instance 會收到 SIGTERM，同樣立刻取消該 instance 上的 run
Cloudflare 125 秒stream 是長連線handler 每 20 秒沒有事件就送 heartbeat；BFF 現在的 withHeartbeat 可以保留
