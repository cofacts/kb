URL Resolver 登入牆調查

staging 換上 Cloudflare Browser Run 之後，幾篇 Facebook 和 Threads 連結存下來的是登入頁或登入彈窗的文字，不是貼文內容。這頁整理每個網址在每一步拿到什麼、原因，以及改用 Browser Run /snapshot 是否有用。

調查日期：2026-11-07 對象：cofacts/url-resolver master（PR #74 之後） 環境：dev.cofacts.tw（staging，Vultr 主機）

結論

  1. FB 分享連結：staging 主機和 Browser Run 都被導到登入頁。/share/p/… 會先轉到 story.php，再從這兩個 IP 被轉到 /login。改用 /snapshot 沒有幫助。從 staging 主機改打 FB 的嵌入貼文端點 plugins/post.php?href=<story.php 網址>，可以拿到完整貼文。
  2. Threads：staging 主機直接請求會收到 429，兩種網址都退到瀏覽器。瀏覽器有看到貼文和正確的 og:description，但頁面蓋著登入彈窗，Readability 有時抽到彈窗文字。網頁網址那篇就是這樣；/share/ 那篇在 staging 剛好抽到貼文，這個結果不穩定。
  3. FB 一般貼文網址：現在從 staging 主機和 Browser Run 都拿得到內容。2ymc8okkg75vj 當初存成日文登入牆，那次的 log 已經不在，原因無法追查。
  4. 不管哪種情況，登入牆文字都以 status: 200、error: null 存進資料庫。被擋的 FB 連結全都存成同一段 footer，在 Elasticsearch 裡彼此高度相似，反而干擾比對。

url-resolver 怎麼處理一個網址

0. 轉址
先跟著轉址走到目標網址。FB 有額外處理：遇到 /login/?next=… 會取出 next，photo.php 會改走嵌入貼文端點。
1. 直接請求
從 staging 主機用 CofactsBot/1.0 User-Agent 抓 HTML，讀 og 標籤。非 200 就算失敗。
2. 瀏覽器
第 1 步失敗或欄位不齊，才用 Browser Run 開啟頁面。summary 取 Readability 抽出的正文，og:description 只在 Readability 失敗時才用。最後和第 1 步的結果合併，title 和 summary 誰長用誰。

同一批網址，四種來源

每列是一個網址。四欄分別是：

  • staging 存下的：資料庫裡的 title 和 summary（取自 dev-api.cofacts.tw），下面附 staging url-resolver log 裡記錄的處理過程。
  • Browser Run /snapshot：直接呼叫 Cloudflare Browser Run 的 /snapshot，讀渲染後頁面的 og:title 和 og:description，沒有經過 url-resolver。每個網址跑兩次，結果相同。/snapshot 只回傳最後的頁面，看不到中間轉址。
  • curl：staging 主機：在 staging 主機上用 curl 抓網頁，User-Agent 設成 CofactsBot/1.0，等於重做 url-resolver 的第 0、1 步，列出每一步的 HTTP 狀態碼。
  • curl：家用網路：同樣的 curl，改從台灣的家用網路發出，用來對照 IP 的影響。

發現一：FB 分享連結的貼文頁，staging 主機和 Browser Run 都要求登入

已驗證

url-resolver 的轉址處理沒有問題：log 顯示兩個 /share/p/ 都正確轉到了 story.php。問題在下一步，story.php 對 staging 主機的 IP 回 302 到 /login。Browser Run 開啟分享連結也一樣停在登入頁。只有從家用網路請求，story.php 才直接回 200 和貼文內容。

瀏覽器那一步打開的是登入頁，Readability 抽到的是頁尾連結，於是存下 title「Facebook」和一段 footer。

可行的解法已在 staging 主機上驗證：把 story.php 網址交給 FB 的嵌入貼文端點，從 staging 主機直接請求就拿得到完整貼文。

curl（staging 主機，CofactsBot UA）

  plugins/post.php?href=<100063950836324/posts/1644700867671592>

  plugins/post.php?href=</share/p/1KfLdr4NqU/>

url-resolver 已經有這套機制，但目前只用在 photo.php。分享連結第一次轉址的 Location 就帶有 story_fbid 和 id，可以在跟去 /login 之前取下來，改走嵌入端點。

發現二：Threads 被限流，瀏覽器看得到貼文卻抽錯區塊

已驗證

staging 主機直接請求 Threads 會收到 429 Too Many Requests，網頁網址和 /share/ 都一樣，所以兩篇都退到瀏覽器那一步。家用網路請求則兩種網址都正常。

Browser Run 開啟後，頁面上有貼文本身，og:description 也正確，但中間蓋著「Say more with Threads」登入彈窗。用 url-resolver 內建的 src/vendor/Readability.js 解析 /snapshot 回傳的 HTML，兩種網址都抽到彈窗：

Readability 解析 /snapshot 的 HTML（兩種 Threads 網址結果相同）
  title: 倉鼠J｜美食探險筆記 (@jamster_eatnfun) on Threads
  text : Say more with ThreadsJoin Threads to share thoughts, find out what's going on, follow your people and more.

staging 的 log 裡，網頁網址存下 107 字的彈窗文字；/share/ 兩次都存到 25 字的貼文內文。兩者在 url-resolver 裡走的是同一條路，同一套 Readability 有時選中貼文、有時選中彈窗，所以 /share/ 會成功只是剛好，不能當成可靠的行為。

og:description 就在同一份渲染後的 HTML 裡，瀏覽器那一步優先讀它，兩種網址都能拿到正確內容，也不必處理 429。

發現三：FB 一般貼文現在正常，當初的登入牆無法追查

待查

2ymc8okkg75vj 的原始網址（含 __cft__ 參數），現在從 staging 主機直接請求就能拿到 og，Browser Run 也拿得到。資料庫裡卻存著日文登入牆，表示當時第 1 步沒拿到內容，退到瀏覽器後又被擋。

staging 的 url-resolver 容器在 11/5 重啟，那次處理的 log 已經不在，無法確定當時是 IP 暫時被限制，還是別的原因。之後若再出現，可以對照當時的 [resolve] log。

讓錯誤內容被存下的程式缺口

以下來自程式碼閱讀，對應 PR #74 合併時寫下的已知限制：「如果瀏覽器也收到登入牆，一般的瀏覽器抽取可能把它的標題和樣板描述帶回來」。

  1. 瀏覽器結果沒有任何檢查。threadsMetadata.js 的佔位判斷只套在第 1 步，scrape() 的結果直接合併。
  2. 瀏覽器那一步不讀 og:description。summary 一律取 Readability 的正文。對社群貼文來說，og:description 才是貼文本身。
  3. 合併時一律取比較長的。ScrapeResult.merge 的 title 和 summary 誰長用誰。Threads 貼文常常很短，約 106 字的彈窗文案就會蓋過真正的內容。
  4. 比對字串過時。程式比對 /^Join Threads to share ideas/，Meta 現在的文案是「Say more with Threads」加上「…share thoughts」。

改用 /snapshot 有沒有用？

沒有明顯幫助。

  • FB 分享連結：/snapshot 一樣停在登入頁。被擋的是出口 IP，換成哪一種 Browser Run 呼叫方式都一樣。
  • Threads：現在的瀏覽器步驟本來就看得到貼文，問題在抽取。/snapshot 回傳的 HTML 一樣蓋著彈窗。
  • FB 一般貼文：第 1 步從 staging 主機直接請求就拿得到，不需要瀏覽器。

建議修法（依優先順序）

瀏覽器步驟優先讀 og:title / og:description 在 scrape() 裡從渲染後的 DOM 先取 og 標籤，缺了才用 Readability。 修好 Threads 兩種網址，不受 429 影響，改動範圍小。
FB 分享連結改走嵌入貼文端點 從 /share/p/ 第一次轉址的 Location 取出 story.php 網址，交給 plugins/post.php?href=…，並從嵌入頁解析貼文文字。 已在 staging 主機上用 curl 驗證拿得到完整貼文。resolveFacebookUrl 目前只對 photo.php 這樣做。
偵測登入牆，偵測到就回傳錯誤 對兩個步驟的結果都檢查 FB 與 Threads 的登入牆文案（含日文等語系）。偵測到就丟掉，兩邊都沒內容時回傳 error，不存成 200。 最後一道防線，避免同一段 footer 灌進 Elasticsearch。
社群網站不讓瀏覽器的長文字蓋過 og FB 與 Threads 已有 og 文字時，合併時保留，不採用比較長的瀏覽器文字。一般新聞網站維持現狀，才能存到全文。 防止未來出現新的登入牆或彈窗文案時，又把正確內容蓋掉。

方法與限制

  • staging 存下的內容來自 dev-api.cofacts.tw GraphQL 的 GetArticle.hyperlinks。
  • staging url-resolver 的 log 用 docker logs 在 staging 主機上讀取。這個容器用的是 json-file log driver，沒有送進 Cloud Logging（staging 的 rumors-api 有送）。容器 2026-11-05 重啟，更早的 log 已經不在。
  • Browser Run 測試使用 POST /browser-rendering/snapshot，waitUntil: networkidle2，逾時 30 秒。Browser Run 的 session API 只列出進行中的 session，查不到 staging 過去的瀏覽紀錄。
  • Readability 測試使用 url-resolver master 內建的 src/vendor/Readability.js，在 jsdom 上解析 /snapshot 的 HTML，和 url-resolver 在瀏覽器內執行的環境不完全相同。
  • curl 一律帶 User-Agent: CofactsBot/1.0 (+https://github.com/cofacts/url-resolver) 和 Accept: text/html,application/xhtml+xml，與 url-resolver 第 1 步相同。
