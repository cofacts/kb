rumors-api PR #411 · backfill 前的評估 · 2026-11-17

圖片 kNN 搜尋評估

文字和圖片可以開始 backfill；影片和聲音先等等。
  • 文字：效果最好。PR 作者 Yutin 的評估中，前 10 名找得到同一則謠言的比例從 24% 升到 70%，幾乎沒有題目變差。文字的費用也最低。
  • 圖片：有幫助，不會弄亂。我們在 100 題實際的圖片查詢上模擬：原本找不到的，前 10 名找得到的從 25 題增加到約 35 題（共 50 題）；原本排第 1 的 50 題全部維持第 1。PR 現在的設定就好，不需要調整 kNN 權重。
  • 影片和聲音：先不要跑。超過約 3 分鐘的聲音一定會失敗，大約占 28%，要先修。影片可以算，但每支的費用是圖片的 6–20 倍，而且搜尋效果還沒評估過。

PR #411 已經部署到 production。圖片的數字是模擬的結果，backfill 完成後要在 production 上用同一批題目實際跑一次確認。開始前要先處理的事，見最後的「下一步」。

為什麼要做這個實驗

PR #411 讓搜尋可以額外用 embedding 找「意思或長相相近」的文章（kNN）。要用 kNN，得先把資料庫裡的文章都算出向量，也就是 backfill。目前 production 只有 1,644 筆有向量，幾乎所有文章都還沒有。backfill 要花錢、也要花時間，所以想先確認值得做。

文字的部分，Yutin 在 PR 上已經評估過（見下一節）。這次的實驗補上圖片，想回答三個問題：

  1. 同一則謠言的另一張圖，如果現在搜不到，加上 kNN 能不能找回來？
  2. 原本就找得很準的題目，會不會被 kNN 弄亂？
  3. 上次擔心的狀況：有些圖逐字稿很像、其實是不同的訊息。kNN 能不能把它們分開？

先了解搜尋怎麼算分

用圖片搜尋時，每篇文章的分數是下面三項加起來，分數高的排前面：

hash 命中
最多 100
逐字稿
常見約 186
kNN
最多 1

kNN 最多只有 1 分，比另外兩項小很多。所以它沒辦法改變已經被找到的文章的順序，只能把原本沒找到、但長得很像的圖，接在結果的最後面。

文字：PR 作者已經評估過，效果很好

Yutin 在 PR 上留了本機評估報告（11/3）。他用 10/25 的 production 資料（29.8 萬篇）在本機架了一個 ES，查詢都經過真正的 GraphQL API，隨機抽 300 篇文字文章當查詢：

第 1 名就對前 10 名找得到完全沒有結果
現在的搜尋16.3%24.0%59.3%
加上 kNN36.3%69.7%0.3%
  • 幾乎不會變差：138 題排名變好，2 題各掉 1 名，沒有任何一題掉出前 10。現在完全找不到的 178 題中，找回了 113 題。
  • 實際準確率可能更高：kNN 排第 1、但被判為答錯的結果，抽樣檢查後約一半到七成其實是同一則謠言，只是連到別的回應。他估計真正「第 1 名就對」的比例約 66–78%。
  • 呼叫端要配合：kNN 只在呼叫 API 時帶 filter.embedding 才會生效。rumors-site 和 cofacts/ai 的 minimumShouldMatch 設得很寬（'1'、'0'），開 kNN 前要先調嚴，否則第 1 名的準確率會下降。這不影響 backfill。

他也評估了圖片：前 10 名找得到的比例從 39.7% 升到 61.3%。不過他的本機環境只有一半圖片有向量，搶位置的無關圖片比 production 少。這次的實驗把這部分也估進去了，結論一致。

圖片：這次的實驗怎麼做

  1. 從資料庫中挑出「至少有另一張圖共用同一則查核回應」的圖片，隨機抽 400 張。共用同一則回應，就代表兩張圖是同一則謠言，這是我們判斷「找對了沒」的標準答案。
  2. 用 public API 拿這 400 張圖去搜尋，記錄現在搜尋的結果和分數，當作「現況」。
  3. 從中挑出三組題目：
    漏網組（50 題）同一則謠言的其他圖，現在用 hash 抓不到。看 kNN 能不能找回來。
    穩定組（50 題）現在第 1 名就是對的。看加了 kNN 會不會變差。
    逐字稿很像組（50 對）逐字稿分數很高、但沒有共用回應的兩張圖。先由 Claude 標註，再由人工逐對複核，判斷是不是同一則。
  4. 用和 rumors-api 相同的設定，直接呼叫 Vertex，算出約 1,770 張圖的向量，其中包括 1,000 張隨機的圖當作「無關的圖」對照組。過程中沒有寫入 production。
  5. 用 PR 的計分方式模擬加上 kNN 之後的排序，並把「無關但剛好很像的圖會擠進來」也算進去。

問題 2 ・ 不會弄亂

穩定組：50 題全部維持第 1 名

因為 kNN 最多只有 1 分，不會超過原本靠 hash 或逐字稿排第 1 的文章。

問題 3 ・ 不需要分開

逐字稿很像的圖，50 對裡有 47 對其實是同一則

剩下 3 對中，有 2 對是同一個詐騙模板的不同個案。人工複核的判斷是「不同但高度相關，收到其中一張的人看到另一張也能察覺被騙，列在一起很有用」。所以這批資料沒有「需要把它們拆開」的問題，排在一起反而是對的。

另一個發現：很多其實是同一則謠言的圖，沒有被連到同一則回應。所以上面的數字都偏保守，實際表現應該更好。

要不要提高 kNN 的權重？不用

我也試了把 kNN 分數放大 50 倍、200 倍，讓它跟逐字稿分數一樣大：

kNN 分數放大漏網組：前 10 名找到穩定組：第 1 名掉下來
1 倍（PR 現在的設定）35 / 500 題
50 倍36 / 501 題
200 倍36 / 503 題

放大之後，漏網組最多只多找回 1 題，穩定組反而開始有題目掉下來。維持 1 倍最好。相似度門檻用 0.6 到 0.8 結果都差不多，維持 PR 用的 0.7 即可。

影片與聲音：還不能跑

聲音：超過約 3 分鐘就會失敗

  • 先前以為錯誤是因為聲音多帶了「只取前 80 秒」的設定（videoMetadata）。實測後發現不是：有沒有帶，結果都一樣。
  • 真正的問題是：只取前 80 秒的設定對聲音沒有作用，Vertex 會把整段音檔送進模型。154 秒以下的音檔都成功，228 秒以上的都回 400 INVALID_ARGUMENT，上限大約 3 分鐘。
  • production 有約 1,170 個聲音檔。隨機量了 60 個，中位數 94 秒，有 17 個（約 28%）超過 180 秒，這些都會失敗。目前 production 沒有任何錯誤紀錄，是因為長音檔還沒送進來過。
  • 修法：送 embedding 前先把聲音截成 80 秒，和影片一致。rumors-api 目前沒有 ffmpeg，要在 Docker image 裡加上，或請 media-manager 產生截短的版本。退路是長音檔先不算向量，它們仍然可以靠逐字稿搜尋到。

影片：可以算，但貴，效果也還沒評估

  • 測了 2 支影片（5.8MB、29.5MB）都成功，只取前 80 秒的設定對影片有作用。
  • 每支約 1,600–5,300 tokens，是圖片（約 258）的 6–20 倍。production 有約 2.1 萬篇影片文章。
  • 目前沒有人評估過影片的搜尋效果，PR 作者的評估也沒有涵蓋影片和聲音。

下一步

  • 已完成PR #411 已隨 release/20261115 部署到 production（api 容器 11/15 啟動，已確認是新版程式）。
  • 先做backfill 腳本加上「只跑指定類型」的選項（例如 --types），才能只跑文字和圖片。
  • 先做backfill 文字（約 23 萬篇）和圖片（約 4.3 萬張）。
  • backfill 後跑完要做 _forcemerge，否則搜尋會變慢。
  • backfill 後用這次同一批 100 題圖片，在 production 上帶 filter.embedding: 0.7 實際搜尋一次，對照模擬結果。
  • 要確認沒有登入的搜尋只能讀已經算好的向量。要確認 LINE bot 搜尋時有帶使用者，使用者新傳的圖才會有 kNN。
  • 要確認rumors-site 和 cofacts/ai 開啟文字 kNN 前，先調嚴 minimumShouldMatch。
  • 之後修聲音超過 3 分鐘會失敗的問題（開 PR）。
  • 之後影片、聲音各隨機抽 50 支試算，量失敗率和每支的費用；再評估影片的搜尋效果，決定值不值得 backfill。

費用參考：這次算了約 1,770 張圖，用了 45.6 萬 tokens，每張約 258 tokens。全部 4.3 萬張圖片約 1,100 萬 tokens。文字每篇只有幾十到幾百個 tokens。實際金額請對照 Vertex 的價目表。

這個評估的限制
  • 搜尋時用的是網站上的縮圖（600px），不是原圖，所以有 13% 的題目連自己那張都沒用 hash 找到。
  • 這次的實驗只評估了圖片，沒有評估影片、聲音，也沒有評估「用圖片找文字文章」。文字的數字來自 PR 作者的評估。
  • kNN 是在本機用精確計算模擬的，ES 實際用的是近似搜尋，結果可能有些微差異。
  • 「無關的圖會擠進來多少」是用 1,000 張隨機圖推估的。
