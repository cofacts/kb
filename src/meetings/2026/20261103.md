### 背景續跑

https://claude.ai/artifact/9pK51sye5vnZjFRqHdC9AY?sk=fnntzCscds1-8GSvljXuNg

<details>
<summary>Artifact 內容摘要：cofacts.ai 背景續跑（2026-10-30）</summary>

> 原始 HTML 存檔：[artifacts/20261103-9pK51sye5vnZjFRqHdC9AY.html](./artifacts/20261103-9pK51sye5vnZjFRqHdC9AY.html)

**結論：** cofacts/ai 架構設計草案。目標是讓使用者關掉瀏覽器後 AI 查核助理仍繼續把 run 跑完，重新打開時接回進度；同一個 session 開在兩個視窗時兩邊都看得到即時輸出。做法是**把「執行 run」和「觀看 run」分開**，以 **Redis Streams 當 run registry，和 rumors-line-bot 共用既有的 Redis**。

**問題（現況）**
- 一個 turn 很長（單次模型呼叫曾跑 195 秒，Cloud Run request timeout 調到 900 秒；turn p90 約 255 秒）。
- run 壽命綁在 HTTP 連線：BFF 把 `request.signal` 轉給 ADK，ADK 2.11 起 `/run_sse` 在 client 斷線時一定中止 run（google/adk-python issue #4029 仍開著）。斷線後只留下已寫入 Postgres 的非 partial event 與一筆 `INVOCATION_ABORTED`，正在打的字遺失。
- 前端寫好但沒用到的 `resumeRun(invocationId)`：實測 ADK resume 時模型看到「Invocation was aborted」，不會接著做完。
- 同一 session 的第二個視窗看不到正在跑的內容。

**設計要點**
- 不用 ADK 內建 `/run_sse`，在 `adk/main.py` 自建 `Runner`（沿用 Postgres 與 GCS 服務）＋自訂 route；`POST /runs` 用 `asyncio.create_task` 開背景 **drain task** 把 `runner.run_async()` 拉到底，每個事件（含 partial）寫進 Redis Stream。
- Redis key（皆加 `cofacts-ai:` 前綴、皆有 TTL）：
  - `cofacts-ai:run:{userId}:{sid}`：鎖，`SET NX PX 30000`，owner 每 10 秒續約；保證一個 session 同時只有一個 run，owner 掛掉 30 秒內自動消失。
  - `cofacts-ai:stream:{userId}:{sid}`：事件 stream，每筆帶 `invocationId`；寫入 `done` 後 30 秒刪除；`MAXLEN ~ 20000` 保險。
  - `cofacts-ai:cancel:{userId}:{sid}`：非 owner 收到停止時設旗標，owner 每秒檢查。
- writer task 每 50 ms 用 pipeline 批次 `XADD`（Cloud Run 連 Redis Cloud 走網際網路，逐筆會拖慢數秒到數十秒）。
- SSE handler：先 `XRANGE` 補送本 run 至今事件（partial 原樣重播，因前端是「接尾巴」合併），再 `XREAD BLOCK` 20 秒等新事件；逾時送 `: heartbeat` 並確認鎖仍在（因 Cloudflare 125 秒閒置會斷線）。不做 Last-Event-ID 續傳，一律從 run 開頭補送。
- 前端合併規則：**正在跑的 invocation 只信 stream，其他 invocation 只信歷史**（歷史用 ADK 內建 session API）。
- Client 三狀態（靜態／查一次／直播中），靜態時不 polling，只在載入頁面、`visibilitychange` 變可見、按送出時查一次 `GET /runs/{sid}/status`；「有沒有新事件」比對 session state 的 `lastEventTime`，不用 ADK `lastUpdateTime`。
- 新 API（BFF 加 `/api` 前綴轉發）：`POST /runs`（202 或已有 run 時 409）、`GET /runs/{sid}/status`、`GET /runs/{sid}/stream`、`POST /runs/{sid}/cancel`、`POST /sessions/{sid}/opened`。舊 `/api/run-sse` 過渡期保留，也是 Redis 連不上時的退路。
- 中斷判定一律看歷史：停止／SIGTERM 時補寫的 event 在 `customMetadata` 標 `cancelled` 或 `interrupted`；後者顯示「中斷了」與重問按鈕。redeploy 收到 SIGTERM 時立即拒絕新 run（503）、取消所有 run 並補寫，10 秒 grace period 足夠。

**各環境 Redis**
- production（GCE）：docker compose 既有的 `redis`（`redis:alpine`，rumors-line-bot 在用），`REDIS_URL=redis://redis:6379`；沒有 volume、沒有 `maxmemory`，所以 key 一定要有 TTL。
- dev.cofacts.ai 與 PR preview（Cloud Run）：連 staging LINE bot 用的 Redis Cloud 免費機器（`rediss://`，放 Secret Manager），不必 `maxScale 1`，但要關 CPU throttling（`run.googleapis.com/cpu-throttling: "false"`）。不夠時退路是 `redis:alpine` sidecar ＋ `maxScale 1`。
- 本機：`docker-compose.yml` 加 `redis`。

**要先處理的衝突：** 打開 session 時前端 PATCH `lastOpenedAt`（`session.$sessionId.tsx:76`、`chatSessions.functions.ts:183-203`）會讓進行中的 run 死於 `StaleSessionError`；改打 `POST /sessions/{sid}/opened`，鎖存在時回 `deferred`、連線結束後再補呼叫。

**其他邊界：** 沒人看的 run 15 分鐘自行 cancel；每人並行 run 超過 2–3 個回 429（用 `SCAN`，不用 `KEYS`）；key 含 `userId` 防止猜 session id 接上；Redis 重啟時 owner 重新取鎖繼續寫。

**容量：** registry 不是瓶頸，容量和今天的 `/run_sse` 差不多；最可能先撞到的是 Vertex 配額（429）、Redis Cloud 免費方案的連線數、event loop（1 vCPU）、url-resolver。上線前要做假 LLM 負載測試、用 Langfuse 算尖峰並行數、查 Vertex 配額。（文中「尖峰每小時 300 turn、平均 90 秒 ≈ 7.5 個並行 run」只是示範假設。）

**要改的檔案：** ADK 新增 `run_bus.py`、改 `main.py`、`pyproject.toml` 加 `redis`；BFF 新增五個 route；`src/lib/chatCache.ts`、`src/hooks/useChat.ts`（刪 `resumeRun`）、`chatSessions.functions.ts`、`service.template.yaml`、`docker-compose.yml`；GCE `env-files/adk` 與 devops GCE.md。

**待決定：** Redis Cloud 免費方案容量／連線數／區域是否夠；run 長度與每人並行上限；靜態時是否改成可見時每 30 秒查一次；是否起草 decision record。

**尚未驗證（僅推論）：** production Redis 實際設定（描述來自 rumors-deploy `docker-compose.sample.yml`）；staging 用 Redis Cloud 免費機器來自團隊記憶、devops 文件未記載；PATCH session 觸發 `StaleSessionError` 只在 ADK 2.12（SQLite）用外部 `append_event` 實測過；每個 run 佔幾百 KB 到 1 MB 為推估。

</details>

### 把 ADK 接到 coding harness

https://claude.ai/artifact/SioyAZdRD6KP8gQjUAN4B3?sk=y7CC7fhbXQ_iGFclLbqpcQ

<details>
<summary>Artifact 內容摘要：cofacts.ai Harness Agent（2026-10-30）</summary>

> 原始 HTML 存檔：[artifacts/20261103-SioyAZdRD6KP8gQjUAN4B3.html](./artifacts/20261103-SioyAZdRD6KP8gQjUAN4B3.html)

**結論（10/30 Langfuse 回測後）：現在不值得投入完整的 H1 或 H3。** 9/18 之後的正式流量中，harness 明顯會改善結果的 turn 只有約 1%（81 個倒讚中 1 個）；倒讚主因是出處錯配與捏造，屬於 cofacts/ai#144（provenance gate）與 writer 模型選擇的問題，harness 反而會讓受影響的 turn 變慢、變貴。方案分析保留，待工作負載改變（PDF／資料表任務變多、跨文件長期研究）時再評估。背景執行與重連另見「背景續跑」artifact。依據為 `cofacts/ai` 程式碼與 google-adk 2.13、claude-agent-sdk 0.2.175 原始碼。

**查核需要的 harness 能力：** 工作區（下載的網頁／PDF／CSV／上傳檔先存檔、需要時才讀）、分段讀與 grep 大檔、PDF 指定頁與圖片、CSV 計算、共用工作區的 subagent 平行查不同主張、長 run 的 context 壓縮與大輸出落地、保留 `draft_factcheck_response` 的 per-claim gate、`{content, sources}` 形狀與 Langfuse trace／讚倒讚。

**五個方案**
- **H1 HarnessAgent 接 Claude Agent SDK**（品質上限高）：自寫 `BaseAgent` 包 `ClaudeSDKClient`（ADK 的 `AntigravityAgent` 是同樣做法）。優點是 Read（含 PDF／圖片）、Grep、subagent、auto-compact 都已調好；缺點是每個 run 一個 `claude` 子程序（官方建議 ≥ 1 GiB）、只能用 Claude、Langfuse 要重接、Gemini grounding 要包成工具。
- **H2 接 ACP**（之後再說）：in-process 工具、hooks、structured output 過不了 ACP；等 Cofacts MCP（cofacts/rumors-api#389）上線後可作為 H1 的另一後端。
- **H3 維持 ADK LlmAgent 自補工具**（原建議先試）：用 ADK 2.13 實驗性 `EnvironmentToolset`（ReadFile／WriteFile／EditFile／Execute）加上自補的 `glob`、`grep`、`read_pdf_pages`、`view_image`、`todo`、`fetch_to_workspace` 與路徑守門、大輸出落地兩個 callback。沒有子程序、Langfuse／callbacks／前端不變、各 agent 可各自選模型；風險在工具描述、system prompt、compaction 與 subagent 分工要靠 cofacts-ai-eval 持續調校。
- **H4 接 managed agent（Claude 或 Gemini Managed Agents）**（備案）：供應商代管 sandbox 與工作區；但工具要做成公開 remote MCP 或 custom tool，callbacks 要改寫。Claude 版在 GCP 只能走 Anthropic-managed（Marketplace），資料只能放 US／global，每 session-hour 另收 0.08 美元、beta；Gemini 版只能用 Gemini、Public Preview、閒置 15 分鐘快照、7 天後刪除。
- **H5 Pi Durable（`@earendil-works/pi-durable`）取代 ADK**（不建議，設計參考）：durable task 與多人 attach 內建，但要新 Node 服務、TS 重寫所有 callbacks，Experimental 且沒有測試、沒有 HTTP server 與官方 Postgres storage。可借鏡：可替換執行環境、工具標註 replay 是否安全、「先快照再 delta」的接回方式。

**三方案共用的工程（應先做）：** 工作區目錄（`/var/lib/cofacts-ai/ws/{session_id}/` 分 `uploads/`、`sources/`＋`manifest.json`、`work/`，掛 host volume）、`fetch_to_workspace`（走 url-resolver、存原文與 manifest、防 SSRF 擋私有 IP 與 metadata server）、路徑守門（先 realpath 再檢查前綴）、環境變數清理、配額記帳、GCS 同步（lifecycle）與 LRU 清理程式（跳過進行中 run，需從 run registry 得知）。關掉 WebFetch（只回傳小模型摘要、不存原文）。

**Sandbox：** docker 只能當外層；SDK 子程序與 ADK `LocalEnvironment` 都繼承 `os.environ`（含 `DATABASE_URL`、Langfuse secret），GCE container 連得到 metadata server 拿 service account token。Shell 分三級：不開 shell（建議起步）→ 專用唯讀計算工具（如 DuckDB）→ 沙箱 shell（H1 bubblewrap 在 docker 內需 `enableWeakerNestedSandbox`；H3 可換 E2B／Daytona／OpenSandbox），且 shell 不應連網。

**Subagent 與 writer 分身（H3）：** 可用 `ai_writer.clone()` 做分身、每個面向各自跑 investigator／verifier，以結構化交接契約回傳；提出修改版 AgentTool（現版 `agent_tool.py:274` 寫死 `InMemorySessionService()`），把子 session 存進 Postgres（app name 如 `cofacts_ai__sub`）並回傳 `child_session_id`，讓 UI 可展開過程、#144 gate 可遞迴收集來源。建議先不做分身，順序：#144 gate → 持久化子 session 的 AgentTool（套在 investigator／verifier）→ 分身。

**Langfuse 回測（有證據的量測＋模型判讀的估計）**
- 資料：1,275 個正式環境 turn（2026-03 到 10-30）、377 筆讚倒讚。
- 延遲：turn p50 67 秒、p90 255 秒；有子 agent 的 turn 中位數 57% 時間花在 investigator（單次 p50 29 秒）與 verifier（p50 38 秒）。
- 成本：turn p50 0.04 美元、p90 0.22 美元；writer 約 60%、verifier 29%。writer 每多一步約 6 秒、0.01–0.03 美元。
- 工作負載：隨機抽樣只有 53% 是新訊息查核；PDF／長文件 4%、數字或資料表 15%、影音 17%；訊息長度中位數 41 字，41% 是 Cofacts 文章連結。
